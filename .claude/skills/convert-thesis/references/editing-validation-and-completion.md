# 编辑、验证与完成

## 形成受控操作

每项操作都要能够回答：修改哪个稳定对象、依据哪条当前任务证据、使用哪个论文事实字段、预期改变什么、如何检查影响。把不确定的操作留在计划中，不要提交给编辑 Tool。

操作顺序遵循依赖关系，而不是固定阶段。第一个候选必须以目标模板为 `input_docx`；先按
当前任务绑定把学生内容放入模板槽位或区域，再生成依赖页码的目录；先应用全局样式，再
处理局部例外。若两个操作可能使同一对象引用失效，分批编辑并在中间重新检查。

## 执行编辑

- 只调用 `mcp__docfit__docx_edit`，并使用当前文档哈希、有效对象引用、明确前置条件和不同于输入的输出路径。
- 跨文档内容使用学生来源对象引用与模板目标锚点；使用 `import_content_objects` 时，
  `input_docx` 是目标模板工作副本，`source_docx` 是只读学生论文。
- 每次提交保持范围可解释；高风险或会改变分页的操作优先小批量执行。
- 核对返回的输出引用、哈希、变更摘要和编辑反馈页。
- 编辑反馈用于发现局部回归，不代表候选文档已经全局验证。
- 只有原子批次 `committed: true` 且后置条件成立时才消费结果；失败时不假定部分操作已成功。

## 验证候选文档

完成编辑后，先取得与最终候选哈希绑定的 `candidate_verification` 视觉证据，再调用 `mcp__docfit__docx_validate`。如果验证失败：

1. 区分输入、权限、陈旧引用、结构错误和视觉问题。
2. 找到最小根因和受影响对象。
3. 只修复有证据支持的问题。
4. 对新候选重新执行受影响视觉复核和验证。

验证产物必须对应最终候选文档；旧候选的成功结果不能复用于新输出。Tool 返回 `status: ok` 只表示调用完成，仍需逐项检查 checks、warnings 和阻断发现。

## 交付决策表

| 状态 | 决策 |
| --- | --- |
| 结构验证通过，视觉复核完成，无阻断冲突 | 可交付 |
| 转换可继续，但缺少会改变结果的学校证据 | 请求最小证据，不交付 |
| 编辑或验证 Tool 失败，无法证明候选状态 | 报告失败，不交付 |
| 存在未解决的内容丢失、遮挡、分页或规则冲突 | 修复后重验；无法修复则不交付 |
| 只有已披露的非阻断差异 | 可根据任务要求交付，并明确说明差异 |

## 最终核验

- 最终 DOCX 位于授权输出目录；
- 最终 DOCX 的候选主干来自目标模板，学生论文只作为内容来源；
- 输出哈希与候选视觉证据、验证结果一致；
- 原始论文的正文语义、引用、表格、图片和脚注没有无依据丢失；
- 所有计划操作都有执行结果或明确的未执行原因；
- 阻断项为零，非阻断差异已经披露；
- 最终回复没有把编辑反馈、局部渲染或单元分析误称为全局完成。
