# 通用论文领域母稿工作区

## 1. 为什么先写母稿

现阶段不应该从四个 Knowledge Reference 文件开始写。四个 Reference 是四种消费视角，
不是四套彼此独立的领域真值。如果先分别写，很容易出现：

- 同一个论文单元在不同文件中使用不同名称；
- 字段目录、样式观测交接和识别方法彼此不完整；
- 为了填满某个 Reference，提前把实现协议误写成领域知识；
- 后续发现缺少单元或样式时，需要同时返工多个文件。

因此，本工作区先建立一份更完整、更细的领域母稿，并以一套分生命周期的语义锚点模型作为
主视图。这里的模型是供上下游按需引用的协作语言，不是 Agent 必须逐字段填写的表单、固定
推理步骤或公共 Schema。它帮助 Agent 把当前材料中的具体内容识别到已知锚点，并据此读取
相关通用经验；具体位置、顺序和必需性仍由当前学校证据决定。样式另由“样式观测与确定性
补全合同”交接模板观察、语义绑定、逐属性来源、国家标准补全和 unresolved，不进入经验库。

产品 Knowledge 提供跨任务稳定的 `semantic_id`、`node_kind` 和 `relation_kind`；
当前任务中的 fact/unit/ref/object 统一使用任务内 `instance_id`；Tool locator 只属于匹配
document hash 的不可变快照。这套模型包含主阅读顺序树、附着内容子树、共享事实、非包含
关系和当前任务投影。它回答：

1. 一篇论文在语义上可能由哪些通用单元组成；
2. 每类单元通常携带哪些内容字段、结构字段、所有权和基数；
3. 语义字段与内容节点形态如何分离，复合对象如何无损表达；
4. 学生内容、模板固定内容、说明文字、生成内容和人工内容如何区分；
5. 内容与模板承载位置怎样关联，未知对象和伴随材料怎样保留；
6. 哪些差异必须留给当前学校材料，哪些概念可以跨学校复用。

母稿完整以后，再从同一来源裁剪出概念、识别方法、解释原则和处理模式。

主阅读顺序树是论文内容顺序的唯一事实；共享事实、关系和保留对象使用侧向视图，当前快照
定位、处置判断、绑定和验证使用任务投影。后面的字段表和验证清单不能另造一套平行目录，
也不能把这些侧向关系重新塞回内容树。

复合前置单元与正文遵守同一顺序原则：封面、题名页、书脊和摘要中的 ref、标签、固定内容、
图形、人工内容和 unknown 进入一个可交错的有序 `children[]`；正文图表也用内部
`children[]` 保存 caption、asset/grid、legend、note、source 和 unknown 的真实穿插顺序，
多语言题名分别建实例并配对。论文关系统一使用单数
`relation.<predicate>` canonical 边，每条边只有一个 source 和一个 target；map/backlink 只由
`relation_index.by_source/by_target/by_kind` 派生。提交包中的 `submission.thesis` 只引用候选
document hash，不复制论文语义树。

## 3. 母稿写到什么深度

母稿采用四层深度：

这里的 L0–L3 是“母稿写到多细”的描述深度，不是论文正文的节点层级。正文自己的
“容器—章节/内容块—行内节点”结构以母稿第 3.5 节为准。

| 深度 | 必须回答 | 例子 |
|---|---|---|
| L0 目的与边界 | 为什么需要这个模型，它解决什么，不解决什么 | 内容、位置和呈现必须分离 |
| L1 领域地图 | 有哪些通用对象、单元、关系和变化点 | 摘要、目录、章节、图、表、公式、参考文献 |
| L2 字段与节点组成 | 每个对象通常有哪些字段、节点形态和子对象 | 摘要正文、关键词、标题、题注、表注 |
| L3 约束与验证 | 基数、所有权、处置方式、允许关系、缺失行为和应验证什么 | 图题与图片关联、目录项由结构生成 |

当前母稿停止在 L3。以下属于未来实现层，不在这里固定：

- Python 类型、JSON/YAML Schema 和数据库结构；
- 某个 Tool 的请求/响应字段；
- OOXML XPath、bookmark、styleId 或 Provider locator；
- 某所学校的字体、字号、页边距、固定文案和顺序；
- “样式观测与确定性补全合同”的物理 Schema、属性目录、国家标准规则表和 Tool 参数；
- 正式 Knowledge 的物理拆分和版本发布方式。

## 4. 母稿怎样填写

任务内论文逻辑实例按照统一层级描述：

```text
任务内论文逻辑实例
├─ 语义目的：它在论文中表达什么
├─ 语义身份：semantic_id + instance_id
├─ 结构形态：section / paragraph / figure / table / scalar / collection 等
├─ 内容字段：文字、标识、日期、媒体、表达式等
└─ 包含结构：所属内容流、直接父实例、顺序、层级和有序 children

当前任务投影
├─ 快照定位：`snapshot_locator` = document hash + locator kind/value
├─ 证据与判断：`evidence.supports`、适用性、冲突、置信度和所有权
├─ 处置与绑定：保留、填充、生成、人工处理以及 `binding.edge`
└─ 验证：怎样确认内容、结构、关系和呈现没有被破坏
```

树中节点统一采用以下紧凑标记：

```text
节点名 `semantic_id` <fact/unit/ref/object/relation> [候选基数；典型来源角色；安全倾向]
```

其中 `fact` 是论文级共享事实，`unit` 是实际文档单元，`ref` 是单元中的事实出现位置，
`object` 是单元自己拥有的内容，`relation` 是非包含连接。树线只表示包含，`→` 表示关系。
方括号只是概念目录提示，实际所有权、出现状态和处置仍由当前任务投影表达。

## 5. 完整性的判断方式

“完整”不表示断言所有论文都具有相同字段，而表示：

- 高频论文单元均有稳定的候选语义名称；
- 每个单元通常需要的信息已经列出；
- 标量、段落、标题、列表、图、表、公式、引用、审阅对象和生成字段均有容纳位置；
- 可选、条件、重复、学校固定和未知扩展均有容纳位置；
- 原始内容、规范化内容和来源关系能够同时保留；
- 新学校只需提供当前任务差异，不需要重新发明整个论文内容世界；
- 未覆盖对象能够以扩展单元保留，而不是被静默删除。

## 6. 后续怎样使用

母稿稳定后再进行两次转换：

1. **领域收敛**：合并同义单元、补齐字段、确认关系和变化点；
2. **Knowledge 投影**：从母稿分别提取概念、识别方法、解释原则和处理模式。

投影时可以删减母稿细节，但四个 Reference 不应重新创造母稿中不存在的领域概念。
