# 论文模板树、内容树与确定性样式体系设计

> 状态：架构草案  
> 范围：只讨论通用的树模型、映射关系、样式解析和兜底机制，不枚举某所学校或某类论文必须包含的具体字段。  
> 核心原则：内容是什么、内容放在哪里、内容怎样显示，必须分开建模；运行时格式必须由确定性规则产生，不能由 AI 临时发挥。

## 1. 要解决的问题

论文模板系统需要同时处理四件事：

1. 用统一结构表达学生论文内容；
2. 找到目标模板中可以承接这些内容的位置；
3. 为每类内容解析出稳定、可复用的目标样式；
4. 当学校没有定义某项样式时，使用系统预设样式确定性兜底。

如果把这四件事混在一起，会产生以下问题：

- 同一种正文格式被复制到大量段落和槽位中；
- 模板位置变化会迫使内容模型一起变化；
- 学校缺少某项样式时，生成器只能猜测；
- 用户内容携带的源格式污染目标学校格式；
- 修改一处学校要求，无法稳定更新全文；
- 无法判断最终样式来自学校、系统兜底还是某次临时修改。

本设计将系统拆成三棵树和一个映射层：

```text
内容树 Content Tree
    │  描述“内容是什么”
    │
    ▼
绑定层 Binding Layer
    │  描述“内容去哪里、以什么角色渲染”
    │
    ▼
模板树 Template Tree ────────── 样式树 Style Tree
    │  描述“模板中有哪些位置”       │  描述“每种角色怎样显示”
    └──────────────┬───────────────┘
                   ▼
            确定性文档渲染器
```

## 2. 核心概念

### 2.1 内容树

内容树是学生论文的通用语义结构。它只描述内容的身份、层级、顺序和关系，不携带目标学校的字体、字号、行距和模板位置。

一个内容节点至少需要表达：

```yaml
node_id: stable-node-id
kind: scalar | block | container | collection | generated | manual
semantic_role: system.semantic.role
value: null
children: []
cardinality: one | optional | many
owner: student | system | school
```

关键约束：

- 内容树中的语义标识必须稳定；
- 可重复内容使用集合或树结构表达，不能为每个实例预设一个固定槽位；
- 内容节点不保存目标学校的 Word 样式 ID；
- 内容节点不保存从用户源文档复制来的字体、字号和段落参数；
- 无法识别的内容必须保留为扩展节点或进入人工复核，不能静默删除。

内容树解决的是：

> 系统当前拿到的这段数据，在论文语义上是什么？

### 2.2 模板树

模板树是目标文档的逻辑结构，不等同于 DOCX 的原始 XML 节点树。它描述模板中哪些部分是固定内容、哪些部分可以填写、哪些部分可以重复、哪些内容由系统生成。

通用模板节点类型包括：

```yaml
kind:
  - fixed
  - inline_slot
  - block_slot
  - block_container
  - repeatable_region
  - generated_field
  - manual_only
  - conditional_region
```

一个模板节点至少需要表达：

```yaml
template_node_id: stable-template-node-id
kind: block_container
locator:
  type: content_control | bookmark | range | field | fixed_anchor
  value: stable-locator
accepts: []
style_policy: {}
empty_policy: keep | remove | placeholder_review | fail
children: []
```

模板树解决的是：

> 目标模板有哪些稳定位置，每个位置允许放入什么结构？

模板树不能反过来定义论文内容模型。例如，模板中只出现一组示例节点，不代表用户正文只能出现一组。示例节点可以作为样式和结构证据，但正文区域仍应建模为可容纳任意数量块的容器。

### 2.3 样式树

样式树是系统所有语义样式角色及其继承关系。内容节点引用语义样式角色，学校包对这些角色提供覆盖，渲染器再将解析结果编译为 Word 命名样式或其他目标格式。

样式节点应包含：

```yaml
style_role: text.some_role
kind: paragraph | character | table | numbering | layout
inherits: text.parent_role
fallback_role: text.generic_role
properties: {}
```

样式树解决的是：

> 这个语义角色在当前学校、当前输出格式中应该怎样显示？

### 2.4 绑定层

绑定层连接内容树和模板树，并指定使用哪个样式角色。它不重复保存完整样式参数。

```yaml
binding_id: stable-binding-id
content_selector: content.path.or.role
target_template_node: stable-template-node-id
insertion_mode: replace | append | repeat | generate
style_binding:
  default_role: text.default_role
  role_map: {}
transform: null
empty_policy: inherit
```

绑定层回答三个问题：

| 问题 | 绑定信息 |
|---|---|
| 放什么 | `content_selector` |
| 放到哪里 | `target_template_node` |
| 使用哪类样式 | `style_binding` |

## 3. 三棵树的职责边界

### 3.1 内容树不负责目标格式

内容树可以声明一个节点是某种标题、普通文本或结构化对象，但不能声明它在某所学校中必须使用某个具体字体。

错误示例：

```yaml
semantic_role: text.body
font: 某字体
size: 12
line_spacing: 20
```

正确示例：

```yaml
semantic_role: text.body
value: 用户正文内容
```

具体参数由样式解析器根据目标学校决定。

### 3.2 模板树不负责复制格式参数

模板节点应引用样式角色，不应在每个槽位中重复一份字体、字号和缩进。

```yaml
template_node_id: main-flow
kind: block_container
style_policy:
  default_role: text.body
```

模板中确实存在局部版式例外时，可以声明受控例外，但必须附带来源和原因，不能把任意直接格式当成模板规则。

### 3.3 样式树不负责内容位置

样式树只定义视觉和排版行为。它不应该知道某段内容位于第几页、第几个内容控件或哪个 XML 路径。

### 3.4 绑定层不拥有业务真值

绑定层负责适配，不负责重新解释内容。如果内容树已经将一个节点判定为某个语义角色，绑定层只能按照配置转换或路由，不能根据字体大小随意改判。

## 4. 内置基础样式体系

### 4.1 为什么必须有系统基础样式

学校模板经常存在以下情况：

- 只在说明文字中描述格式，没有建立对应的 Word 命名样式；
- 某类内容在模板中没有示例；
- 示例段落错误地使用了其他命名样式，再靠直接格式覆盖；
- 同一种语义内容在不同位置出现互相冲突的格式；
- 学校只定义了部分属性，例如字体和字号，没有定义行距或分页规则。

因此，系统必须为每个受支持的语义样式角色提供一份完整的基础样式。学校样式是对基础样式的覆盖，而不是从空白开始填写。

系统基础样式需要满足：

1. 每个受支持角色都能解析出完整样式；
2. 每个属性都有确定值或确定的继承来源；
3. 不依赖 AI 在运行时补齐；
4. 可以被学校配置按属性覆盖；
5. 可以追踪每个最终属性的来源。

### 4.2 基础样式不是所有学校共用一套最终格式

系统基础样式的作用是兜底，不是取代学校要求。

```text
系统基础样式
    + 学校通用覆盖
    + 学校角色覆盖
    + 经批准的模板局部例外
    = 最终解析样式
```

学校有明确定义时，以学校定义为准；学校没有定义时，缺失属性继续继承系统基础值。

### 4.3 样式属性必须支持三态

学校覆盖中的每个属性需要区分：

| 状态 | 含义 |
|---|---|
| 缺失 | 沿继承链继续查找 |
| 明确值 | 使用学校指定值 |
| 明确清除 | 清除父级属性，例如取消粗体 |

不能把“学校没有写”解释成零、空字符串或由 AI 猜测。

示意：

```yaml
school_overrides:
  text.some_role:
    properties:
      font_east_asia: 指定字体
      bold:
        mode: clear
      # line_spacing 缺失，因此继承基础样式
```

## 5. 确定性样式解析

### 5.1 解析优先级

样式按照从低到高的优先级合并：

1. 系统根样式；
2. 系统语义父样式；
3. 系统当前角色基础样式；
4. 学校级通用覆盖；
5. 学校当前角色覆盖；
6. 模板中有明确证据、经过批准的局部例外。

运行时禁止增加第七层“AI 猜测”。

伪代码：

```text
resolve(style_role, school, template_context):
    chain = build_inheritance_chain(style_role)
    resolved = merge(system_root, chain)
    resolved = merge(resolved, school.global_overrides)
    resolved = merge(resolved, school.role_overrides[style_role])
    resolved = merge(resolved, approved_template_exception)
    assert resolved is complete
    return resolved
```

### 5.2 角色级兜底链

某个专用角色在学校中没有定义时，应沿预设的 `fallback_role` 查找，而不是直接落到 Word 的 `Normal` 样式。

```yaml
style_role: text.specialized_role
fallback_role: text.generic_role
```

兜底链必须满足：

- 在系统配置中显式声明；
- 不允许循环依赖；
- 最终必须到达一个完整基础样式；
- 每次使用兜底都生成可审计记录；
- 严格验收模式可以要求学校显式确认正在使用的兜底项。

### 5.3 无法兜底时的行为

如果出现系统不认识的样式角色，并且没有明确的兜底链，系统必须：

1. 保留原内容；
2. 标记 `needs_review`；
3. 阻止严格模式下的最终交付；
4. 输出缺失角色和相关内容节点；
5. 等待人工补充映射或扩展样式定义。

禁止以下行为：

- 随机选择相似样式；
- 直接使用上一个段落的格式；
- 静默落到 `Normal`；
- 让 AI 根据名称临时生成字体和字号；
- 把用户源文档的直接格式作为目标学校样式。

## 6. 学校样式的产生过程

学校样式配置可以由程序和 AI 辅助提取，但提取结果不是运行时真值。候选样式需要经过证据合并、冲突处理和验证后，才能写入学校样式注册表。

### 6.1 有效样式计算

对于 Word 模板，候选有效样式至少需要合并：

```text
文档默认值
→ 命名样式继承链
→ 当前命名样式
→ 段落直接格式
→ 段落默认字符格式
→ 文字 run 直接格式
```

不能只读取 `styles.xml`，也不能直接复制某个示例 run。

### 6.2 证据来源

每个学校样式覆盖应记录：

```yaml
evidence:
  source_file: source-id
  source_location: stable-location
  evidence_type: normative_text | effective_example | raw_style | inferred
  confidence: confirmed | review_required
  reviewed_by: null
```

只有进入学校样式注册表的确定性配置才能参与运行时渲染。

### 6.3 冲突处理

同一角色出现多个不同样式时，不做平均，也不自动选择出现次数最多的值。处理顺序为：

1. 使用明确的学校规范；
2. 使用学校模板中的可见说明；
3. 比较官方示例的有效样式；
4. 判断是否应拆成两个不同语义角色；
5. 无法确定时进入人工复核；
6. 复核完成前使用系统基础样式并明确标记来源，或在严格模式中阻断。

## 7. 模板节点与样式的关系

### 7.1 节点引用角色，不复制样式

模板节点推荐保存：

```yaml
style_policy:
  role: text.some_role
  resolution: school_then_system
```

不推荐保存：

```yaml
style_policy:
  font: 某字体
  size: 12
  line_spacing: 20
```

后者会让相同样式在大量节点中重复，无法统一修改。

### 7.2 容器节点允许多角色

一个富内容容器不能只有一个样式。它需要声明允许的内容类型及对应样式角色：

```yaml
style_policy:
  default_role: text.body
  role_map:
    semantic.heading: text.heading
    semantic.paragraph: text.body
    semantic.caption: text.caption
```

内容树中的每个子节点决定自己的语义角色，模板容器只负责校验该角色是否被允许。

### 7.3 模板级默认样式作用域

模板树可以在父节点定义默认样式作用域，子节点继承：

```yaml
template_node_id: document-region
style_scope:
  default_paragraph_role: text.body
  default_character_role: text.inline
```

这种继承只继承样式角色，不复制最终物理参数。

## 8. 用户内容进入目标模板的流程

```text
用户输入
  ↓
内容解析器：识别语义，不保留目标无关的直接格式
  ↓
通用内容树
  ↓
绑定解析器：匹配目标模板节点
  ↓
样式解析器：系统基础样式 + 学校覆盖 + 已批准例外
  ↓
目标格式编译器：生成命名样式、编号、段落、表格和字段
  ↓
结构验证 + 样式来源审计 + 真实渲染验收
```

### 8.1 用户源格式处理

用户上传文档中的格式主要用于识别语义，不直接成为目标格式。

默认策略：

- 移除源段落样式 ID；
- 移除源字体、字号、行距、缩进等版式参数；
- 保留有明确语义的行内标记，例如强调、上下标、超链接和公式结构；
- 将语义节点映射到目标学校样式角色；
- 由目标学校样式注册表生成最终格式。

### 8.2 占位符样式必须隔离

模板占位文字只能使用专门的占位符样式，例如 `system.placeholder`。填入用户内容时必须删除占位符内容及其直接格式。

禁止让以下属性从占位符泄漏到用户正文：

- 灰色文字；
- 提示文字字体；
- 示例粗体；
- 示例下划线；
- 示例段落缩进。

### 8.3 固定内容例外

学校固定表单、签字区域和不可泛化的版式对象可以保留模板原有结构及局部格式。这些对象需要标记为 `school_owned`，不进入普通正文样式归一化流程。

## 9. 目标格式中的样式落地

以 Word 为例，段落级格式应优先编译为稳定的命名样式：

```text
系统语义角色
→ 学校解析样式
→ 稳定 Word styleId
→ 段落通过 w:pStyle 引用
```

渲染规则：

- 普通段落只引用命名样式；
- 标题的层级、编号和目录语义由样式及编号系统控制；
- 字体、字号和行距不在每个 run 中重复写入；
- 只有真正的行内语义才使用字符样式或受控直接格式；
- 模板中已有的错误样式不能因为名称相似就直接复用；
- 同一语义角色在同一文档中应解析为同一有效样式。

## 10. 样式来源与审计

每次生成都应输出样式解析清单：

```yaml
resolved_styles:
  text.some_role:
    target_style_id: stable-style-id
    source_chain:
      - system.base
      - school.override
    fallback_used: false
    unresolved_properties: []
```

当使用系统兜底时：

```yaml
resolved_styles:
  text.another_role:
    target_style_id: stable-fallback-style-id
    source_chain:
      - system.base
    fallback_used: true
    fallback_reason: school_style_missing
```

审计结果至少需要回答：

- 最终使用了哪个样式角色；
- 样式参数分别来自哪里；
- 是否使用系统兜底；
- 是否存在学校模板冲突；
- 是否存在待人工确认项；
- 是否出现未经批准的直接格式。

## 11. AI 的边界

AI 可以参与离线辅助工作：

- 建议内容节点的语义分类；
- 从学校模板中提出候选样式；
- 发现样式冲突；
- 建议某个未知角色可能使用哪条预设兜底链；
- 生成需要人工复核的问题清单。

AI 不能参与运行时最终决策：

- 不能临时决定字体、字号和行距；
- 不能绕过样式注册表写入直接格式；
- 不能在缺少映射时静默选择“最像”的槽位；
- 不能把未审核候选样式直接写入最终论文；
- 不能因为文档视觉上大致相似就跳过结构和样式来源验证。

AI 的候选结论必须被固化为版本化、可测试、可审计的配置后，才能进入生产渲染链路。

## 12. 扩展机制

通用内容树和样式树应覆盖高频结构，但不追求一次性穷举所有学校特例。

扩展必须显式命名：

```yaml
semantic_role: extension.namespace.custom_role
```

扩展规则：

1. 扩展节点仍需声明类型、父角色和兜底角色；
2. 扩展不能修改通用角色的既有语义；
3. 多个学校重复出现的扩展可以提升为系统通用角色；
4. 未知扩展内容必须保留并进入复核；
5. 扩展样式缺失时仍走确定性兜底或明确失败。

## 13. 版本与兼容

三棵树和绑定层分别版本化：

```yaml
content_schema_version: 1
template_tree_version: 1
style_schema_version: 1
binding_schema_version: 1
```

版本升级要求：

- 稳定语义标识不能无迁移地改名；
- 删除角色前必须提供替代角色；
- 修改兜底链需要回归所有学校包；
- 学校包必须声明兼容的系统样式版本；
- 生成结果记录使用的全部版本号；
- 历史模板可以通过迁移器升级，不能依赖运行时猜测。

## 14. 验证规则

### 14.1 内容树验证

- 所有节点类型合法；
- 稳定 ID 唯一；
- 父子关系和基数合法；
- 未识别内容没有被静默丢弃；
- 可重复内容没有被错误压缩成单值字段。

### 14.2 模板树验证

- 所有定位器唯一且可以找到目标；
- 容器允许的节点类型明确；
- 空内容处理策略明确；
- 固定、手工和系统生成内容的所有权明确；
- 模板示例数量没有被误当成内容实例上限。

### 14.3 样式树验证

- 所有样式角色均可解析；
- 继承链和兜底链无循环；
- 系统基础样式完整；
- 学校覆盖只包含合法属性；
- 清除属性与缺失属性能够区分；
- 每个最终属性都有来源；
- 未经批准的直接格式为零。

### 14.4 绑定验证

- 必需内容能够找到目标模板节点；
- 内容类型与槽位类型兼容；
- 所有使用的样式角色都能解析；
- 可重复内容使用重复区域或块容器；
- 同一内容不会被意外写入多个互斥位置；
- 使用兜底的绑定会进入审计报告。

### 14.5 输出验证

- 命名样式引用全部有效；
- 用户内容没有残留占位符样式；
- 用户源文档的版式参数没有污染目标格式；
- 系统生成字段仍保持可更新语义；
- 修改一个命名样式能够统一影响所有对应内容；
- 严格模式不存在未解决角色；
- 目标应用中的真实渲染结果通过验收。

## 15. 推荐的运行模式

### 15.1 宽松生成模式

适合草稿和模板接入阶段：

- 允许使用系统基础样式兜底；
- 明确显示兜底报告；
- 未知内容保留为复核标记；
- 不宣称已经完成学校级格式验收。

### 15.2 严格交付模式

适合最终论文交付：

- 所有必需内容完成映射；
- 所有使用的兜底已被学校包显式接受；
- 不存在未知样式角色；
- 不存在未经批准的直接格式；
- 样式来源、结构和真实渲染全部通过验证。

## 17. 分阶段落地建议

### 阶段一：冻结树模型

1. 定义内容节点、模板节点和样式节点的共同字段；
2. 定义绑定结构；
3. 定义节点类型、基数、所有权和空内容策略；
4. 定义扩展命名空间和版本机制。

### 阶段二：建立系统基础样式

1. 为所有系统样式角色建立完整基础值；
2. 建立语义继承和兜底链；
3. 实现三态覆盖；
4. 实现完整性和循环依赖验证。

### 阶段三：实现学校适配

1. 从模板抽取逻辑节点和候选有效样式；
2. 将候选结果固化为学校覆盖配置；
3. 建立内容到模板节点的绑定；
4. 为冲突和缺失项生成复核清单。

### 阶段四：实现确定性渲染

1. 将用户输入转换为通用内容树；
2. 按绑定写入模板树；
3. 解析并编译目标命名样式；
4. 清除用户源格式和占位符格式；
5. 输出样式来源和兜底报告。

### 阶段五：建立回归门禁

1. 正常样式、缺失学校样式、部分属性缺失和未知角色测试；
2. 兜底链循环和无终点负向测试；
3. 多层重复正文结构测试；
4. 用户直接格式污染测试；
5. 目标应用真实渲染测试。

## 18. 已确定的设计结论

1. 系统先定义通用内容树，学校模板不能重新定义内容世界；
2. 模板树描述位置、结构能力和空内容策略，不重复保存物理样式；
3. 内容节点和模板节点通过绑定层连接；
4. 样式以系统语义角色为索引，以学校覆盖为差异；
5. 系统必须提供完整基础样式，学校只覆盖有证据的部分；
6. 缺失学校样式时使用预设继承和兜底链，不调用 AI；
7. 未知角色无法确定性兜底时必须进入人工复核或阻断严格交付；
8. 用户源格式只能辅助识别语义，不能直接成为目标学校格式；
9. 最终文档优先使用命名样式，直接格式只用于受控的行内语义和学校固定例外；
10. 每次生成都必须说明最终样式来自系统、学校还是经批准的模板例外。

## 19. 一句话总结

> 内容树决定“是什么”，模板树决定“放在哪里”，样式树决定“怎样显示”，绑定层负责把三者接起来；学校没有定义样式时，系统沿预设样式继承链确定性兜底，无法兜底就明确报错，绝不让 AI 在运行时自由发挥。
