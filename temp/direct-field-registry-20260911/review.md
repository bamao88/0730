# 完整语义表与拆分示例：直接 API 复测

2026-09-11。结论：补齐任务合同后，**中文题名单独请求 3/3 正确，耗时 3.15–3.38 秒**；同一提示下，8 条原文合在一个请求仍有语义错误。应继续检验输入组织造成的差异，不能用前一轮缺少语义表的实验判断模型能力上限。

## 补上了什么

- [完整字段语义表](semantic-table.json)：当前 Registry v0.5.0 的全部 54 项，保持原顺序，未只挑本页命中字段。保留 field_id、label、meaning、content_type、cardinality、parent_field_id（如有）、value_sources、allowed_part_roles。仅移除供宿主核对的 hash、digest 和重复常量；来源证明另存 [vocabulary-provenance.json](vocabulary-provenance.json)。
- [完整 JSON 示例](examples.json)：4 组、5 条不同字面原文。对照固定封面标题与独立题名占位；标签与完整学号值分开；作者姓名、导师姓名、导师职称分别绑定；年级专业班级按已定义复合字段整体绑定。每例均给完整 parts 和真实 field_id，例子的 text 按顺序逐字拼回原文。
- [完整提示词](system-prompt.txt)：说明拆分单位是“一个字段的完整值或一种非填写责任”；语义表不是本页应出现字段清单，不能为凑表新增槽。格式说明与其约束对象单独表达。

上一轮虽提供过通用示例，但没有完整字段语义表，也未把具体 field_id 与输出粒度连起来。尤其姓名/职称两个字段，与年级专业班级一个复合字段的区别，不能要求模型在没有这份定义时自行猜出。因此上一轮只能算输入不完整的探索，不能代替按实际任务合同的验证。

## 如何测试

沿用同一个 MiniMax-M3 直接 HTTP 接口，关闭推理，temperature=1，max_tokens=4000，无工具、Skill 文件读取、Agent SDK 或历史会话。

首先将原先的 8 条真实原文共同发给 API，重复 3 次：校名、固定封面标题、中英文题名、学生姓名、学号、班级、指导老师及职称。随后保持 system 和全部语义表/示例逐字不变，只把实际输入缩为其中的中文题名一条，再重复 3 次。

完整表与示例共约 1.36 万字符；混合请求实际输入约 4294 token，单条请求约 4102 token（以 API 缓存/非缓存统计合计为准）。这不是靠只筛几个答案字段来缩短请求。

## 实际结果

| 检查项 | 8 条混合请求，3 次 | 单条中文题名请求，3 次 |
| --- | --- | --- |
| 总耗时 | 8.553 / 6.686 / 9.661 秒 | 3.197 / 3.384 / 3.151 秒 |
| 中文题名完整填写范围 | 0/3；均误判固定文字 | 3/3 正确 |
| 英文题名填写范围 | 1/3 正确 | 未测试 |
| 学号标签与完整值 | 3/3 正确 | 未测试 |
| 班级标签与复合字段 | 3/3 正确 | 未测试 |
| 导师姓名与职称分开 | 1/3 正确 | 未测试 |
| 校名、固定封面标题 | 3/3 正确保留 | 未测试 |
| 整组验收 | 0/3 | 3/3，仅此单条任务 |

单条中文题名的三次输出一致完成以下核心判断：

```json
{
  "items": [{
    "n": 6,
    "parts": [
      {"text":"毕业论文（设计）中文题目","role":"fill_slot","field_id":"thesis.title.zh"},
      {"text":" （小二黑体加粗）","role":"style_only","note":"约束中文题名"}
    ]
  }]
}
```

note 字面有轻微差异，原文、角色、字段和范围均正确，三次都逐字覆盖。

混合组需要分开归因：

- 第 1 次：题名均固定化；学生姓名标签中的格式说明留在 fixed_label；导师范围转为 manual_region，公开 note 误以为不能拆开姓名和职称，尽管本轮示例明确允许并示范了拆分。
- 第 2 次：题名均固定化；“×××□教授”整体绑定 advisor.name.zh，会吞掉职称。
- 第 3 次：英文题名与导师拆分正确，中文题名仍固定化；姓名与中文题名各漏一个普通空格。后者是机械完整性问题，不与漏字段混为一谈。

三次混合输出均使用约定 items 对象，已输出 field_id 都来自真实语义表且角色允许。输出结构合规不等于语义正确。

## 能得出什么

1. 本病例的字段识别和完整替换范围，可以在关闭推理、直接 API、几秒的请求里做对。不能说必须用数分钟推理才能完成。
2. 语义表定义了字段边界，完整示例定义了如何把这些边界落实为原文 parts；两者都应成为后续测试的固定基础输入。
3. 此轮同时补了表与示例，不能独立归因于其中一个。单条与混合组的 system 相同，输入组织是下一步可验证的差异；当前样本还不能证明具体是哪条邻近文本造成影响，也不证明所有字段独立请求都可靠。
4. 本次是**真实 API 语义小样本实验**，不是原生 real replay、E2E agent loop 或 product acceptance。没有修改生产 Skill、运行配置和拆分策略。

每次请求、原始输出、API usage 和计时均保存在对应 `registry-examples-*`、`single-zh-*` 目录。耗时含网络与服务端处理；请求使用 standard tier，自动缓存命中如实记录，不能视为性能 SLA。
