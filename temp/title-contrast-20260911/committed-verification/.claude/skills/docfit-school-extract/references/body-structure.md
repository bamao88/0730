# 正文代表结构

## 用途

帮助 Agent 从学校模板中选择最小、真实、可复用的正文代表结构，保留学校展示的标题层级、正文段落、
图表公式列表等样式能力，同时清理多余写作样例。

## 触发条件

- unit 已被识别为正文、正文样本、章节结构、图表公式列表或类似正文能力承载区，需要继续拆解。
- 模板包含多个具名章节或写作样例，需要提炼成一个可复用正文接口。
- 标题层级、正文段落、图表、公式或列表样式需要作为学校样式事实。
- Word 样式名、编号外观、目录关系或页面布局给出不同层级信号。
- 清理样例前，需要确认正文能力仍有真实承载结构。

## 核心判断规则

### 目标

正文模板表达可重复的写作能力，不复制学校源模板中的每个具名样例章。通常用一个
从当前 `field_id_vocabulary` 识别出的正文容器/结构接口承载本校真实展示的代表成员：

```text
正文容器/结构字段
├── 章标题成员字段
├── 一级节标题成员字段
├── 二级节标题成员字段
├── 普通正文成员字段
└── 本校确有依据的图、表、公式、列表等代表成员
```

这不是代码固定的“第几章”规则。先理解学校材料，再选择最能代表通用正文的一个物理连贯块。
正文 unit 下钻必须按本 Reference 判断；通用模板文字分类只能辅助区分说明、示例和占位，不能替代
正文成员、层级、代表块和逐块绑定判断。

### 快速路由摘要

- 正文 unit 下钻先判断正文代表结构，不用通用模板文字分类替代正文成员、层级和代表块选择。
- 正文代表结构用 scoped ordered `body_structure` parts 表达；学校分支写在 `reason` 或 `open_questions` 里。
- `parts` 必须按文档顺序一一表达正文成员；重复成员类型也逐块列出。
- 目录缓存、样式名或编号外观只能作为证据之一，不能单独替 Agent 决定正文层级。

### 选择方法

- 优先选择不绑定具体主题的通用演示；若没有，比较多个具名区域，选择能表达本校层级与版式的
  最小代表集合。
- 成员来自同一个结构上连贯的学校正文块，并按真实文档顺序提交。不要从不同章拼接出虚构结构。
- 标题层级综合显式编号、相对视觉层级、要求文件、TOC 关系和上下文判断；Word 样式名相同不证明
  层级相同，编号外观也不能脱离学校上下文成为代码规则。
- 先保住每种关键版式的唯一承载依据，再清理其他写作样例。文献综述、结论等具名模块通常复用同一
  正文能力，但学校若明确赋予特殊结构责任，则保留其真实差异。
- 图表、公式、列表、引文等只在本校材料确实展示且后续填充需要时增加，不因 Registry 有字段就
  凭空创建。

### 层级判断示例

常见中文论文正文用阿拉伯数字和点号表达层级。只在学校材料没有给出相反证据时，按下面方式判断：

```text
1 前言 / 2 ×××× / 5 结论 -> 当前输入词表中的章标题成员字段
2.1 ××××                 -> 当前输入词表中的一级节标题成员字段
2.1.1 ××××               -> 当前输入词表中的二级节标题成员字段
□□…… / 含 [1] 引用的段  -> 当前输入词表中的普通正文成员字段
（1）……                  -> 正文段内列表或普通正文成员；不能当作独立标题层级，除非学校材料明确要求
```

注意：`2 ××××` 和 `2.1 ××××` 不是同一层级。`1 前言`、`2 ××××`、`5 结论`
通常同属章标题；`2.1` 才是下一层节标题；`2.1.1` 是再下一层标题。

### 物化口径

由 Agent 明确选择结构锚点、按文档顺序的成员 part 与每个成员的输入词表 `field_id`。
受控编辑能力只执行已经明确的机械修改；它不替你挑选代表或推断层级。

若后续上下文表明更好的代表块，先比较全局影响，避免为了局部
样式改进丢失已经证明的成员类型。

### 输出要求

正文代表结构 judgment 要能被直接消费。不要只输出 "outline1=..."、"outline2=..." 或自然语言说明；
优先用 `source_entry_id` 指向代表正文 source entry，并把每个被保留为正文结构成员的可见文本按文档顺序写成
`body_structure` part；只有一个判断必须横跨多个 source entries 时，才用兼容 `scope.reading_range_id`
指向代表正文 view range。需要字段的 member part 只能写输入词表中
`usage_affordance.allowed_part_roles` 含 `body_structure` 的 `field_id`。同一个 `reading_block`
最多只能有一个带字段的 `body_structure` 成员 part；编号、空格/分隔符、格式说明和固定模板文字若必须拆出，
用 `fixed_label`、`style_only` 或 `cleanup` 表达，不要再次绑定同一个正文成员字段。不要输出单独的结构 ID、成员列表或兼容字段别名。

如果学校模板展示了多套正文编号或学科分支，不要把分支写成新的字段或结构 ID；分支只能写在
`reason` / `open_questions` 里。正文成员字段只能来自当前 `field_id_vocabulary` 中允许
`body_structure` 的 exact `field_id`；不要把 `unit-body:block-0020` 这类 `reading_block_id`
放进 `field_id`。

可执行形态。下面的 `输入词表中的...字段ID` 是占位说明；真实输出必须复制 unit packet 中的
exact `field_id`：

```yaml
source_entry_id: source-entry-body-sample
parts:
  - text: "1 前言"
    role: body_structure
    field_id: 输入词表中的章标题成员字段ID
  - text: "□□……"
    role: body_structure
    field_id: 输入词表中的普通正文成员字段ID
  - text: "2 ××××"
    role: body_structure
    field_id: 输入词表中的章标题成员字段ID
  - text: "2.1 ××××"
    role: body_structure
    field_id: 输入词表中的一级节标题成员字段ID
  - text: "2.1.1 ××××"
    role: body_structure
    field_id: 输入词表中的二级节标题成员字段ID
  - text: "□□……"
    role: body_structure
    field_id: 输入词表中的普通正文成员字段ID
reason: >
  1 前言和 2 ××××同为章标题，2.1 为节标题，2.1.1 为下一层标题，
  省略号正文和含引用正文为普通正文成员。
```

如果同一个结构块里有多个相同类型成员，也要逐块列出。不要把多个章标题压缩成一个 part，
也不要把多个正文段压缩成一个 part；下游需要每个成员的
真实样式载体。

### 反馈修复

如果宿主反馈正文结构成员与 reading block 不能一一对应，重新读取反馈列出的正文块，并只修这个
body structure judgment：

- 保留同一个代表正文语义，除非学校语义本身判断错了；
- 按反馈中的 `reading_block_id` 文档顺序重写 ordered parts；
- 每个 `reading_block` 最多保留一个带字段的 `body_structure` member part；不要把同一标题的编号和标题文字拆成两个同字段正文 member；
- 若反馈指出多个分散 `body_structure` intents 不可执行，把同一代表正文块合并为一个
  `scope.reading_range_id` judgment，并在其中按顺序列出全部 `body_structure` parts；
- 为每个成员 part 写一个对应的输入词表 `field_id`；
- 若某个 block 不应该成为正文结构成员，把它从这个 judgment 中移出，并单独给出保留、删除或
  unresolved 判断；
- 若反馈指出字段不可消费，把 part 的 `field_id` 改成输入词表中的安全字段，或返回 `needs_input`；
- 学校分支、学科 track、编号体系或适用条件放到 `reason` / `open_questions`，不要制造新字段 ID；
- 若反馈指出 `open_questions` 未清，只保留会改变学校语义判断的问题。Word 承载方式、Registry 合同维护、
  物化 handler 能力或发布风险属于宿主实现问题，不写入 complete judgment 的 `open_questions`；
- 不要返回分类总结或解释文字来替代逐块绑定。

### 复核

- 结构在最终 Word 中只有一个有意的可复用实例；
- 每个成员都来自当前学校材料并有清楚角色；
- 结构外没有因样例清理遗漏而残留的重复正文接口；
- 删除具名样例后仍保留学校要求的固定标题/章节责任；
- 结构内样式、顺序、分页、表格和节边界有明确语义预期；后续物化复核由宿主完成。

## 反例

- 把“第 1 章”“第 2 章”等多个具名样例都保留为独立可填写接口，导致下游以为学生必须填写多个
  示例章。
- 把 `2 ××××` 和 `2.1 ××××` 归到同一种节标题成员字段，抹掉了学校通过编号表达的章、节差异。
- 写成 `outline1=1 前言/2 ××××/5 结论；outline2=2.1 ××××`，但没有给出每个
  可见成员对应的 ordered part 和输入词表字段，导致后续无法执行。
- 只因为两个标题使用同一个 Word 样式名，就把学校通过编号、缩进或目录关系表达的层级差异抹平。
- 从不同章节各抽一个段落拼成一个不存在于原模板的“完美结构”。
- Registry 中存在图片或公式字段，就在学校没有对应依据时凭空制造代表对象。

## 不负责事项

- 不规定具体编辑动作、工具参数或对象包装实现。
- 不决定最终内容填写如何展开学生章节数量。
- 不保存某个学校样本的正文结论；这里只提供判断方法和边界。
