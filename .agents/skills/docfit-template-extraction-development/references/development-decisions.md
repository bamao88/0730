# 开发判断示例

以下均为模板提取开发的判断示例，不是固定流程、当前能力清单或按原文字串编码的依据。“历史”来自此前讨论；其余为设计示意。

| 情境 | 会带偏开发的选择 | 应作的工程判断 |
| --- | --- | --- |
| 新能力：学校表单出现有顺序、不同职责的多个导师位置 | 只给 Agent 加提示，或按标签文字硬编码新字段 | 查清学校含义、输入词表、判断表达、接口形态、填写合同和下游消费是否一致；新增字段或合同要验证旧资产兼容，不能以 JSON 可输出宣告支持。 |
| 语义判断：一个表单既有基础信息填写位，也有人工签名与评语区 | 按表名整表归为人工区，或让清理/填写按固定优先级覆盖其他用途 | 提供足够原文与布局上下文，让 Agent 判断局部责任；兼容义务共同履行，真实冲突返回修订，不能由工具便利性决定用途。 |
| 样式交接：学校唯一的行距规则写在待清理说明里 | 先删干净，等最终填写器缺样式时再补默认值 | 先识别规则及作用范围，由工具取证并交接到样式合同，再清理；不能丢失学校依据，也不能由模板提取擅定通用兜底样式。 |
| 产品质量：模板能打开、字段检查全绿，但填写后标签丢失或分页错乱 | 用结构检查通过解释为完成，或仅加更多日志 | 验收原学校内容、接口实际填写及版式；查明判断、范围、样式或执行的偏离，修对应能力。生产出文件不是交付完成。 |
| 历史：图片定位正确，但执行器扩大到段落；局部文字修改被整控件接管 | 宣布整个身份体系失败，按样例加分支，或在拦截后宣布修好 | 保留已有身份结论，分别确认操作机制与影响范围；补齐忠实执行能力。不同操作是否同根因要另证，原合法任务成功才算修复。 |

这些例子共享的不是某个修法，而是交付责任：设计要覆盖所需能力与交接，实现要兑现原意，验收要看实际产物。
