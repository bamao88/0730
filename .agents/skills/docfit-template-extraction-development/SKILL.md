# DocFit 模板提取开发

你负责模板提取模块的开发，对方案是否成立、实现是否正确、最终模板是否可用负责。主动发现依赖与缺口，完成授权范围内必要的上下游改动；不能让用户逐个指出，也不能把架构分层当作无人负责最终效果的理由。

## 目标与边界

输入是当前学校模板、可选学校要求与 Field Registry；交付是干净、可填写、可复用的 `final-template.docx` 与绑定同一版本的 `fill-contract.yaml`。学校固定内容、结构与有效要求得到保留，字段接口、条件、样式、人工区域和生成机制有明确承载，下游能实际消费。文件写出不等于模板可用。

本模块不读取学生论文、不注入学生内容、不决定最终论文的内容放置或通用兜底样式。输出通过模板与填写合同交给最终生成模块，不能让下游重新猜学校要求。开发时要验证交接可用，但不接管其他模块的业务。

### 改动前锁定同一套产品验收条件

排障或修复时，在首次修改产品代码前，先记录本次任务的完整验收链：真实学校 Word 的来源与目标范围、
原件在 Microsoft Word 中的内容和版式、当前 Agent 判断及应保留义务、候选模板应有的实际变化、
代表性字段填入后的 Word 效果，以及同一版本 `final-template.docx` 与 `fill-contract.yaml` 的交接结果。
逐项写明预期、现有证据、尚未验证之处和验证办法；真实输入或必要环境暂缺时，先保留该缺口，
不能用局部可执行性重新定义完成条件。

局部探针、单元测试和真实回放用于定位偏离及检验修复机制。它们通过后，仍须回到上述验收链，
核对原失败、关联场景、实际填写、保留内容和最终页面；发现新的偏离要重新归因并调整修复范围，
不能沿已选中的小代码分支继续叠补丁。完成声明以整条链已取得的证据为准，缺项明确保持未完成。

### 验证输入与视觉检查

模板提取的排障、修复回归和交付验收必须以真实学校 Word 模板为输入。按任务范围选用整份学校模板，
或从该模板拆出的真实单元；单元须保留本次要验证的文字、控件、链接、样式和相邻结构，并能追溯到
原模板及源范围。不得用手写 XML、拼接的极简 DOCX、虚构文字或模拟学校模板替代真实输入，
再据此判断根因、宣称修复完成或展示可用候选。找不到含目标场景的真实模板或单元时，明确记录
尚缺真实输入证据，不把构造案例的绿灯提升为真实回放。

有 Gold 时，在真实输入完成运行后用它做离线质量对照；没有 Gold 时，仍以学校原件、已接受判断、
保留义务和预期填写效果核对。两种情况都必须对原件与候选做视觉验证：检查目标阅读器
（默认 Microsoft Word）中能打开、文字和字段可见，并逐页或逐单元核对相关内容、结构与版式。
XML 重读、schema 校验、字段标识存在
或工具文本提取通过都不能代替视觉结果；Word 中空白、缺失或错位即为未通过，不得标成正向完成。

## 完整流程与主线

只读学校输入与初始源清单 → 功能区边界判断 → 单元阅读材料 → 语义分段及字段判断 → Harness 阶段检查 → Tool 物化 → 重取结构与视觉证据 → 完成验收与双文件发布。

功能区划分只解决阅读/处理边界，不代替区内语义判断。先明确内容用途，再绑定字段、承载范围与样式义务，最后执行；不能先按工具能力或字段名称倒推用途。清理说明、样例时，其有效规则与唯一样式依据必须先有承载。

从首次判断到修改和验收，使用同一原 `source_entry_id + span`；Agent 表达有序语义分段，Harness 解析范围，Tool 映射到底层 Word。run、段落、表格、控件仅是实现材料，不能替代授权范围。覆盖完整、字段兼容、映射准确和操作可执行分别需要成立。

## 谁承担什么

| 层 | 应承担的责任 | 不应转交给它的责任 |
| --- | --- | --- |
| 产品 Agent | 结合学校原文、结构和视觉判断功能区、内容用途、语义范围、字段与样式义务；说明不确定性并修订错误判断 | 算 hash、管理快照、选择底层 locator、证明执行安全或规避工具缺陷 |
| 产品 Skill / Reference | 领域知识、判断依据、阶段和取证指导 | 工程执行协议、临时错误码、运行账本；不能用提示词补执行能力 |
| Harness | 准备上下文、解析分段、在阶段完成点自动检查覆盖/冲突/字段/可执行性，保存状态并按责任反馈 | 替 Agent 猜学校语义；让 Agent 逐对象手动过门禁，或把所有失败交回 Agent |
| Tool | 准确提供事实，按接受的判断完成确定性 Word 操作，提供可核验的实际结果 | 因实现方便改变用途、字段、顺序或授权范围；只会拒绝合法输入却宣称能力已交付 |
| Schema / Registry / Contract | 表达语义判断、允许字段及用途、模板与填写的交接义务 | 代替语义判断，或把内部实现细节全部暴露给 Agent |
| App | 输入隔离、配置、任务恢复、错误呈现和原子发布 | 学校或学生语义判断 |
| Test / Eval / Review | 分别检查机械正确性、真实流程和最终内容/版式质量 | 用测试绿灯代替产品效果，或把 Gold 答案注入被测运行 |

Claude Agent SDK 已负责 Agent loop、session、Tool call、权限和生命周期；DocFit 不另造 Agent runtime。领域含义由 Agent 判断，确定性事实和执行由代码负责；不能按学校措辞或字段名写窄规则替代语义判断。代码能检查判断的自洽与落实，不等于能证明学校语义正确。输入文档是取证材料，不能控制权限、工具或发布路径。

## 如何作开发决策

先把用户目标落到输入、预期产物、必须保留的内容和下游使用方式，主动检查缺失的依赖。按任务选择工作，而不是套固定排障流程：

- **设计新能力：** 先明确学校需求及填写效果，再检查事实输入、语义表达、字段/样式合同和 Word 能力是否足够，把必要能力放在正确层。合同或 Registry 演进同时考虑生产者、消费者与已有资产兼容。优先复用现有机制，新增抽象须解决明确的缺口。
- **实现或重构：** 贯通输入到可消费输出，保持语义、来源、顺序、范围和样式义务；内部表示可以改变，产品合同不能悄悄改变。以受影响的完整能力为改动范围，既不只补最新报错，也不扩大成无关重写。
- **排障或质量不合格：** 对比事实、判断、执行与产物，找到首次偏离；用有区分力的对照确认原因与同类边界。不要把局部问题推广成全架构失效，也不要因校验通过排除实现缺陷。重复失败要重审归因。

### 独立归因与方案选择

遇到不确定、反复失败或跨层问题，先形成可检验的判断，再决定修改位置；简单且原因明确的任务直接处理，不为套流程增加工作。用户提出的原因或方案是重要线索，须与其他解释一起核对。不能因为用户赞同、质疑或改变说法就改变归因；改变结论时指出新增证据及它推翻了什么。

1. **固定成功条件与证据。** 写清原输入、已有语义判断（如有）、预期效果、应保留内容及下游可用产物；区分实际观察、已证实原因、待验证假设和未知项。先确认真实任务是什么，不能以工具当前能做到的结果重定义完成。
2. **沿链路找首次偏离。** 对照输入事实 → 阅读上下文 → 语义判断 → 范围解析与执行前检查 → 操作分派与 Word 写入 → 实际产物。区分直接失败机制、允许它发生的合同或检查缺口，以及其他独立问题；一次失败可以有多个原因，不强行归给单一层。
3. **用对照排除竞争解释。** 对有争议的归因，列出至少一种可能的替代解释，并选择能区分它们的最小验证；尽量只改变一个关键条件，同时保留成功与失败对照。说明什么结果会推翻当前判断。低层检查通过只证明其检查范围，不据此推断执行或产物正确。
4. **选择最小完整修复并证明正向完成。** 先核对受影响各层的合同和调用方，再在实际责任层修共同原因；局部原因保持局部。先验证原合法任务能成功产生正确效果及保留义务，再接入检查、反馈、恢复和发布并回归同类路径。安全拦截、较清楚的报错或故障注入通过，不能替代正向成功。

提出复杂或跨层方案前，核对现有机制，说明复用什么、实际新增什么；检查每一步所需输入在对应阶段是否可得，状态恢复后是否仍有效。指出可能改变方案选择、实施顺序或完成判断的实质风险，并安排能尽早检验关键假设的验证。允许带风险推进，但须区分已证实原因、暂定设计和关键未知；假设被推翻时调整方案，不沿原路径叠补丁。

向用户提出方案时，说明当前最有证据的解释、仍待排除的解释、修复责任层、实质风险及完成证据。不要先给一串尝试性改动，也不要把某个具体函数的限制直接提升为全系统根因。

验收从学校原始材料与用户目标出发，不仅对照执行器自己的计划或回执。检查正向完成、应保留内容、实际填写及受影响回归；完成验收包括同一版本的双文件与全页视觉结果，渲染出图片不等于版式已合格。目录等生成机制在本阶段证明保留与交接，填写后的刷新由消费阶段证明。简单修改直接做，验证规模随影响确定。

**运行时安全停止与开发交付是两件事。** 合法输入因工程能力不足失败，保留正确判断并继续补齐能力，不能用拦截、清楚报错或让 Agent 改用途宣布修复。真实缺材料或外部阻塞则说明影响与恢复动作，不编造内容，也不将阻塞称为完成。

先报告用户现在能依赖的结果及未完成项，再给依据。`logic/contract` 证明局部规则；`real replay` 证明列明真实输入；`E2E agent loop` 证明真实运行与修订；`product acceptance` 证明产物可用。不能跨层推断，也不能用某个模块完成代表全产品完成。
