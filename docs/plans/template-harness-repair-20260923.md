## 目标、范围与依据

目标：让学校语义判断能被忠实接收、准确检查、可追溯地修订，并让最终发布与实际验收程度一致。
SDK 继续负责 Agent runtime；本计划只修 DocFit 的领域合同、检查、修订组织、执行与发布边界。

范围包括本次审计的六项问题，以及直接相关的既有用途锁、候选版本和逐轮反馈留档缺口：

| 编号 | 问题 | 主责 |
| --- | --- | --- |
| A | 自动补全文字会扩大既有用途的适用范围 | Harness 判断规范化和覆盖检查 |
| B | 不支持的 Word 执行能力被反馈为要求改变语义 | Harness 失败路由；Tool 能力合同 |
| C | 新修订会话未默认收到上一版判断及关联上下文 | Harness 修订任务构造 |
| D | 局部文字错误发现偏晚，局部与全局重试预算相互牵连 | Harness 检查调度和停止策略 |
| E | 反馈转换隐藏内部术语时丢失原因和责任归属 | Harness / Tool 错误合同和转换器 |

## 阶段顺序与通用门槛

执行顺序：阶段 0 → 1 → 2 → 3 → 4 → 5。
各阶段的验收材料写入各自记录，不能用最后一次全量通过覆盖前面的失败或缺证据。
阶段 1—3 可以进入后续工程工作，但尚不能宣称产品可用；阶段 4 关闭发布检查缺口；阶段 5 才做整体验收。

每阶段要求：明确当前 checkpoint、主责层、最小改动、失败出口、验证层级和剩余风险；完成内聚改动后
只提交相关文件，并记录 commit。修改 SDK 能力设计时先查模块指南列出的官方文档。
Agent-facing 修改必须同步相应合同、feedback sanitizer 或测试，不能只加提示词。

## 阶段 0：固定复现证据与修复合同

**目标：** 把六类发现转为可重复检验的问题，冻结后续各阶段的成功标准。

**涉及层面：** Test / replay、Docs；只读核对 Harness、Tool、App，不改变运行行为。

**工作：**

1. 为 A—G 建立用例矩阵，记录输入、当前行为、应有行为、责任层、所需证据层级。
2. 选取英文摘要重复分段的原始 task root，校验源、inventory、判断与当前合同绑定；无法取得完整
   逐轮消息时明确记为历史缺证据，不重建成假历史。缺少当前合同的真实用例时从真实输入重新运行。
3. 固定 HUNAU / NJAU / PKU 输入及 Registry 摘要，区分普通段落、表格内部、同载体混合用途、跨单元条目。
4. 给失败出口定义内部类别：可修订判断、学校证据缺失、执行能力不支持、系统映射/状态故障、环境故障、
   预算耗尽。内部类别不作为产品 Agent 的记账任务。

**验收：**

- A—G 每项都有可执行断言或明确的真实证据获取步骤；已确认行为与风险推断分开。
- A 的漏掉实质文字、C 的修订基线缺失、E 的原因被泛化、F 的未复核发布至少有确定性复现。
- 真实 replay 用例能绑定输入和真实判断来源；人为修改的判断明确标注“真实载体故障注入”，不算自然 E2E。
- 未读 Gold 来形成运行时答案；工作区已有无关修改和 DOCX 不纳入提交。

**风险与处理：** 旧资产可能与新身份合同不兼容。不得静默迁移旧 proof 后当作当前验证；应重跑输入准备，
保留缺证据状态。没有真实用例时可以完成逻辑复现，但不能关闭真实验证门。

## 阶段 1：修正判断安全边界

**目标：** Harness 不替 Agent 扩大用途，也不为通过执行检查而要求语义降级。覆盖 A、B、G 的用途锁。

**涉及层面：** Harness 主责；Tool / materializer 能力反馈、App 失败状态、反馈合同、Test。
Schema 仅在现有结构确实无法表达失败/修订时调整；Skill 默认不改。

**工作：**

1. 移除“已提交 parts 只有一种用途即可自动补成全文”的推断。只保留能证明不改变用途范围的精确传输处理；
   空格也不能仅因外观不可见就自动继承角色。未判断的实质文字必须返回修订。
2. 解除仅由 exact-text 错误触发的 role / field_id 冻结。允许同一受影响条目的用途变化，并重新检查整条及关联约束。
3. 把语义错误、执行不支持、映射/环境错误分流。工具不支持时保留语义候选，停止相关执行并报告工程阻塞。
4. 删除强制将字段用途改成非字段用途以适应执行限制的指令；确有歧义时可以询问语义，但不得暗示过门答案。
5. 不扩大 Tool 能力声明；缺少的 Word 操作登记为独立能力任务，不靠放宽发布门绕过。

**验收：**

- `logic/contract`：标签后漏掉字段值、cleanup 后漏掉保留正文等反例不会自动扩大用途；缺口仍被明确报告。
- `logic/contract`：合法的新 role / field_id 可进入重新检查；未知字段、错误范围、重叠仍被拒绝。
- `logic/contract`：执行不支持不消耗语义重试，不修改原判断，不进入发布；可纠正的判断错误仍能返回 Agent。
- `real replay`：真实摘要分段与真实表格/混合载体判断在同一输入上回放；对照修复前后判断和执行范围。
  接受正确闭合或准确工程阻塞，不要求所有不支持结构突然变为可发布。
- 只有 contract 通过而 real replay 缺失时，本阶段记为“代码完成、真实验证未完成”。

**风险与处理：** 显式失败数量可能增加，因为之前的自动补全掩盖了缺口；取消用途锁也可能带来修订漂移。
不得以“通过率降低”为由恢复不安全修复；用重新检查保护范围和字段，后续阶段补全版本对比。

## 阶段 2：补齐可追溯的修订和准确反馈

**目标：** 每次修订有足够上下文，系统能解释为何修改、为何拒绝、下一步归谁。覆盖 C、E、G 的记录缺口。

**涉及层面：** Harness 修订包和候选账本、Tool / Harness 错误合同、App 持久化/恢复、Agent-facing 输入合同、Test。

**工作：**

1. 修订包包含相关完整源文、上一版相关判断、冲突判断、必要相邻文本/布局、当前词表、具体问题和可修改范围。
   长文本使用可获取的明确续页；不能只截断后让 Agent 猜剩余内容。
2. 新会话直接获得修订基线；未改变的内容由 Harness 保留。候选版本、父版本和冲突检测留在内部账本。
3. 支持说明连带修订需求，由 Harness 构造扩展上下文、重新开放必要范围，并重跑受影响约束；不允许任意越界写入。
4. 保存各次候选提交、实际发出的修订包、检查结果、差异、接受/拒绝原因；包括被拒绝和 needs_input 的结构化结果。
   不要求记录模型隐藏推理。持久化失败必须可见，不能记录成功后才发现候选不可恢复。
5. 反馈转换保留“发生什么、影响哪里、谁负责、下一步”；映射故障不能变成泛泛的语义重判。
6. 恢复后不得把待修订候选当最终接受结果。老账本缺少必要版本信息时明确重启语义阶段或拒绝恢复，不猜造历史。

**验收：**

- `logic/contract`：在空白新会话条件下，修订包本身包含完成任务所需的旧判断和源文。
- `logic/contract`：拒绝、接受、needs_input、过期修订、范围扩展与中断恢复均可追溯；无关判断保持不变。
- `logic/contract`：sanitizer 同时满足内部信息边界与原因/归属保真；工程故障不路由到语义重试。
- `real replay`：以真实候选构造并检查实际修订包，记录每次合并后的差异与完整检查结果。
- `E2E agent loop`：至少一例自然发生的真实修订从反馈到新判断闭合；若未自然触发，另记真实输入故障注入的
  恢复测试，不能用它替代自然闭环。工程能力阻塞另验证为准确停止。

**风险与处理：** 原文留档增加存储和敏感内容暴露面；使用 task-local 证据，普通日志保留摘要，沿用权限隔离。
上下文过大可能影响修订质量，按关联范围提供完整材料，避免全量堆入。账本升级可能破坏旧恢复，必须显式版本检查。

## 阶段 3：前移局部检查并拆分重试预算

**目标：** 尽早发现可确定的错误，不让互不相关的问题挤占修订机会。覆盖 D。

**涉及层面：** Harness 局部/全局检查、调度和停止策略；App 配置与状态；Test / observability。

**工作：**

1. 每批收到候选就检查 shape、词表、精确原文分段和局部范围；跨批次覆盖、冲突、执行组合仍在汇总阶段检查。
2. 局部和全局调用同一底层校验规则，避免维护两套判定逻辑；局部通过不等于全局接受。
3. 分开管理问题/受影响范围的修订次数与整次运行预算。问题身份由 Harness 根据稳定范围及类别维护，不能由 Agent 改名重置。
4. 同时设置总时间/调用上限和重复无进展停止条件；预算原因单独报告，不能伪装成需要学校补资料。
5. 保存中断时的有效候选及待修订状态，恢复不重复已完成且依赖未变的工作。

**验收：**

- `logic/contract`：第一个批次文字错误在后续批次启动前被发现；跨批次冲突在汇总时仍能阻止执行。
- `logic/contract`：三个互不相关错误分别拥有修订机会，仍受任务总上限限制；同一无进展错误不会无限重试。
- `logic/contract`：角色变化、范围扩大和恢复不能绕过已有预算或全局检查。
- `E2E agent loop`：真实多批次输入记录检查时机、调用次数、停止原因及恢复行为。耗时只作测量，不用一次快慢宣称提升比例。

**风险与处理：** 过早执行跨范围规则可能误拒合理判断；预算过松增加成本，过紧压缩有效修订。
用明确的局部/全局规则划分与阶段 0 样本校准，不能仅调大次数掩盖不可行动反馈。

## 阶段 4：补齐最终视觉检查与发布门

**目标：** 最终 DOCX 在当前候选上完成实际页面复核；未复核不能当作已验收发布。覆盖 F。

**涉及层面：** App 发布主责；Harness completion review；视觉 Tool、检查结果合同、Test。
现有模块合同已经要求最终 render 和全页视觉检查，本阶段落实该要求。

**工作：**

1. 复用现有固定 LibreOffice 渲染和视觉证据工具，绑定最终候选摘要，取得实际页数和全页证据。
2. 实施前明确复核执行者与判定标准：使用现有可用视觉审查能力；若不足，明确要求人工复核并阻断自动完成。
   渲染成功、页面 ID 齐全、空 findings 都不能单独证明已看过页面或版式无问题。
3. 复核范围覆盖缺页、意外空白页、内容溢出/遮挡、文字方向、表格、公式、分页及受保护布局的变化；
   每页或相关页面组有实际检查结论和证据。
4. 区分未检查、通过、阻塞和待人工确认；最终模板及 fill-contract 只在既定发布门满足后一起发布。
5. 候选变化使旧复核失效。视觉问题归因后返回相应修复层：语义问题走语义修订，物化问题修工具，环境问题修环境。
6. 对 LibreOffice 近似渲染歧义保留 Word 实机复核出口；没有证据不能以“只是渲染差异”放行。

**验收：**

- `logic/contract`：未复核、漏页、旧候选复核、存在阻塞项、渲染不可用均不能通过最终发布门。
- `real replay`：真实候选完成渲染与复核记录绑定；修改候选后旧记录被拒绝。
- `E2E agent loop / completion`：真实输入经过语义阶段、物化、最终复核、发布；明确记录哪些检查由人完成。
- `product acceptance` 切片：真实普通文本、表格、公式和多 section 页面经过检查；至少保留一条真实版式失败被拦截的证据。
  没有自然失败时可注入真实候选版式故障，但必须注明为故障注入。

**风险与处理：** 耗时和渲染依赖增加；近似渲染可能误报，模型视觉判断也不能证明所有版式正确。
对歧义明确停止等待复核，避免 silent bypass；机械检查和人工验收状态分开记录。不得为了保留旧成功率弱化发布门。

## 阶段 5：三校完整闭环与产品验收

**目标：** 证明这些修复在组合后仍可用，并明确“修复验收”和“整体产品验收”的区别。

**涉及层面：** 跨层集成 Test、real replay、E2E、离线 Eval（若有适配当前输入的 accepted Gold）、human product acceptance、Docs。

**验收矩阵：**

| 层级 | 必须交付的证据 |
| --- | --- |
| logic/contract | A—G 正反例通过；受影响模块 lint/type/check 通过；最后运行适当的仓库回归，环境失败不得计为通过 |
| real replay | 三校真实 task root、inventory、真实判断回放；摘要分段、表格能力边界、修订基线和最终候选均可追溯 |
| E2E agent loop | 三校各一次当前代码的完整输入运行；至少一例自然修订闭环；中断恢复、工程阻塞和无进展停止分别留证据 |
| product acceptance | 每个待签收案例都有 final-template.docx、fill-contract.yaml、执行/检查证据与最终全页复核，确认实际填写接口和保留内容符合学校要求 |

三校完整输入指本轮固定的完整学校模板，不用逻辑单元矩阵冒充完整模板运行。

   等静态条件能通过上述 20 组实际失败输入。语义覆盖和映射成立，却不足以证明该执行器可完成任务。
   修复应使就绪检查消费实际可执行结果/能力绑定，不能只追加静态拒绝条件。

没有证据支持将这些失败归为 source ID 迁移失效或 Agent 语义优先级问题。编译按整条分类仍需逐 part

核对的语义问题；不通过工具容器选择或人为优先级消解。

#### 修复边界

补齐上述共同文字执行能力及其控件分派，让每个原 span 的义务得到执行；Harness 的就绪依据与 Tool
实际能力同步。保留独立原范围验收，复用现有发布、Word 包校验及视觉复核。Agent 仍选择语义和字段，
Harness 校验范围/字段/冲突，Tool 兑现修改；不新建对象身份，不按个别原文字串写分支，不预设重写
整个 Word 引擎。跨段、域、非文字复合结构等是否需要同一改动，以合同和专项验证确定，不能从这
40 组推广为所有 Word 结构已支持。

#### 必须按证据推进的顺序

1. **确定共同合同及受影响入口。** 对现有角色和承载结构列明应发生的效果、保留内容、样式/生成
   依赖及字段归属；确定所有共用文字编辑器的调用入口。将语义矛盾与合法但能力缺失的任务分开。
   出口：已确认原因能解释失败与成功对照，同类边界清楚，无需改 Agent 正确判断即可表达目标。
2. **先证明共同修复路径可行。** 在既有执行边界上做最小正向验证，同一机制完成控件内局部填写、
   清理、混合用途及关联嵌套场景，并实际填写新字段，证明保留内容和 Word 结构仍正确。涵盖整控件
   复用、已正常跨 run 和多范围组合的回归。出口：一类操作正向完成，而非某个例子通过或全部改成拒绝。
   如未通过，修正归因/方案，不沿失败实现继续增加特例；具体算法在此证据之后收敛。
3. **接入完整 Harness/Tool 链。** 每个原判断义务有可执行对应，执行前就绪与真正执行一致，组合
   操作不会互相破坏；在隔离候选上执行、重读并按原范围核验，成功候选进入后续阶段。旧缓存/恢复
   不绕过新能力合同。出口：原义务完整兑现，已有正常能力不退步。
4. **回到真实输入与真实 Agent 流程。** 原失败任务及关联真实模板分别回放，保留原输入与正确判断；
   真实语义冲突走实际反馈修订，不能手改答案或将切片说成整校通过。能力问题由开发修复，未完成不
   关闭任务；首版语义正确与实际反馈修订证据分开记录。
5. **完成产物交接验收。** 对最终 DOCX 和 Fill Contract 做接口级实际填写验证，检查结构、样式、
   生成机制、保留内容及全页视觉结果，全部绑定同一产物版本。当前 generated-content 策略记录不
   等于已经刷新：模板阶段证明机制/交接有效，消费阶段证明刷新效果，不混淆模块职责或完成时点。
   出口：可用产物及对应证据；人工签收按原流程，未完成层级不得冒称完成。
