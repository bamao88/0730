# DocFit Agent 指南（中文副本）

> 本文是仓库根目录 `AGENTS.md` 的中文人工阅读副本。两者如有差异，以
> `AGENTS.md` 为 Agent 执行权威；修改执行规则时应同步更新本文件。

## 研发期间的文档权威层级

- `docs/docfit-00-index.md` 至 `docs/docfit-06-development-roadmap.md`
  是持续维护的全局开发基线，既不是不可修改的历史归档，也不是七份权威性完全相同的文档。
- 解决设计问题时应按以下层级判断，而不是只看文件名：
  1. 用户最近一次明确批准的决策；
  2. 全局产品与架构不变量，主要由 00 综合说明、由 01 定义；
  3. 由 01、02 和 06 定义的跨模块契约、里程碑范围、安全边界和测试层级；
  4. 当前开发模块已经批准的设计与验收契约；
  5. 02–05 及模块计划中的 Skill、Knowledge、Tool、数据、Eval 和实现细节；
  6. 现有代码、旧测试、示例和历史状态。
- 高层架构约束低层模块设计。当前模块计划不得暗中违反全局产品边界。如果确实需要违反，
  应在实现前停止工作，并将其作为一项明确的架构决策提交给用户，同时说明产品和工程后果。
- 在上述顶层边界内，已批准的当前模块设计是实现权威，可以有意替换 02–05、早期计划、
  现有代码、公开 Tool/CLI 细节、schema 和测试中的过时详细说法。不得利用旧实现细节削弱或
  重新解释已经批准的设计。
- DocFit 处于活跃研发期。除非用户明确批准某个真实外部使用方的迁移要求，否则绿地开发和
  替换式开发不保留旧别名、双 schema、适配器、fallback、双读写路径、废弃路由，或仅用于
  旧版本兼容的测试。可以复用符合新契约的底层原语，但不得复用会扭曲新设计的旧公开契约。
- 修改全局架构、项目布局、跨模块 Tool/CLI 边界、测试层级或里程碑范围之前，必须阅读
  00、01、06 以及所有受影响的专项文档。每项差异都要归类为需要修正的意外违规，或需要
  用户批准的有意设计变更。
- 在隔离设计阶段，用户明确批准的候选目录可以暂时作为该模块的权威，而不必立即改写
  00–06。生产切换时，必须在同一次变更中原子替换旧实现，并更新所有受影响的 00–06 文档、
  消费方、测试、README 和 active capsule。完成标准包括删除被替代的路径；不得让代码领先
  于文档，也不得把兼容性清理留作未来技术债。
- `docs/status/active/**` 只记录精简的执行状态、证据和阻塞项。它不定义架构，也不能覆盖
  已批准的设计。

## 持久化 Agent 记忆

- 本文件是编码 Agent 共享的项目本地启动记忆。`CLAUDE.md` 通过导入本文件使用这些规则，
  而不是维护第二份副本。
- 稳定规则和指针保存在这里；当前里程碑证据和临时阻塞项保存在
  `docs/status/active/**`。
- 项目目前没有 Serena 或 gbrain 记忆库。除非它确实已经配置并经过检查，否则不得声称
  已将记忆同步到其中。

## 证据门控开发协议

- 开始实现变更前，必须识别当前工作包的开发门，并记录在 active capsule 中：
  G0 产品契约、G1 能力契约、G2 组件/Tool 证明、G3 最小垂直切片、G4 Agent 编排，或
  G5 质量 Eval。这些是证据成熟度门，不是产品运行时状态，也不是 M0–M5 的别名。
  完整契约见 `docs/docfit-02-testing-and-iteration.md`，里程碑依赖规则见
  `docs/docfit-06-development-roadmap.md`。
- 后一开发门只能使用前一开发门已经批准且有证据支持的结果。计划文本、代码存在、一次
  Agent 成功或实现声明本身都不构成开发门证据。
- 实现之前，先决定产品边界、公开接口、所有权、副作用、失败语义和延后集成的接口接缝。
- 在可行情况下，通过 schema、enum、fixture、稳定错误码和契约测试，把能力契约变成
  可执行契约。未列出的能力默认不受支持。
- 在开始 Agent 工作流测试前，Tool 单元测试、契约测试和集成测试必须能够在没有 Agent 的
  情况下通过。Agent 成功不能证明 Tool 契约正确。
- Agent 测试验证 Tool 选择、调用顺序、ref/hash 传递、失败处理、产物完成状态和最终回答
  一致性，不能替代内容质量 Eval。
- 质量判断属于 Eval 层。机械上有效或已冻结的产物，只有在绑定到该确切产物的独立 Eval
  通过后，才能被认定为质量合格。
- 每个重要未知项都必须归类为：现在决定、通过有边界的实验验证，或在明确接口之后延后。
  不得暗中把未知项变成实现假设。
- 如果实现暴露出更早层级的契约缺失或错误，应停止当前开发门，返回受影响的开发门。
  不得在后续层级扩大公开接口或绕过该契约。
- 每个开发门结束时都要生成 Gate Report，包含契约基线、变更范围、验收到测试的映射、
  命令与结果、剩余未知项、文档漂移和 PASS/FAIL 结论。当前开发门、基线、证据和阻塞项
  应保存在 `docs/status/active/**`，而不是本文件。
- 跨越产品、公开契约、架构或里程碑开发门必须获得用户明确批准。在已经批准且保持契约
  不变的实现工作包内部，可以自主推进。

## 用户协作画像

- 用户是产品经理和创业者，也是产品与技术的综合决策人。用户熟悉产品、业务和 Agent
  系统，但不是程序员，对传统软件开发的实现细节相对不熟悉。
- 应按技术内容本身所需的深度，向用户提供严肃、专业的技术信息。不得淡化实现细节、架构、
  失败模式或证据，也不要依赖过度简化的比喻；用户能够接受技术深度。
- 在技术决策、任务总结、评审和日常回答中，应额外提供相关的软件工程系统视角和产品决策
  视角，帮助用户看清对用户价值、范围、可维护性、架构、交付风险、运营成本、可逆性和
  未来选择空间的影响。
- 沟通方式应像 CTO 向 CEO 汇报：先说明可选方案、权衡和后果，再说明推荐的实现路径。
- 这些额外视角必须具体并能支持决策，而不是泛泛而谈。在有助于决策时，应区分已确认事实、
  技术建议和更广泛的产品/工程影响。

## 协作与交付纪律

- 在方案或设计讨论阶段保持只读。只有在用户明确要求实施或修改之后，才能修改代码、文档、
  配置、测试、生成产物或仓库状态。
- 实现变更经过验证、确认可用后，立即只暂存本任务范围内的改动，创建 commit，并推送当前
  分支。不得包含工作区中原有的无关改动。如果 commit 或 push 无法完成，应报告准确的
  阻塞原因和仓库剩余状态。
- 实现任何与 Agent 有关的修复或新能力之前，必须先定位本地 Claude Agent SDK docs 目录，
  阅读与任务相关的 SDK 官方文档。该步骤是强制要求，因为 SDK 的演进速度快于模型训练知识
  的更新速度。项目文档、已安装的类型定义和记忆只能作为补充证据，不能替代相关官方文档。
  如果本地 docs 目录或相关官方文档缺失，应在编码前停止并向用户报告文档缺口。

## 当前执行边界

- 权威里程碑契约是 `docs/docfit-06-development-roadmap.md`。
- M0、Provider 无关的通用 Knowledge Package v1、P1、M1 和 M2 均已验证。当前产品开发
  范围已经完成至 M2 `docfit convert` 链，包括该链所需的非 Eval 安全、证据和报告支持。
- 冻结的 M2 基线记录在 active development capsule 中。M2 之后的 O0.0–O0.7 隐私安全
  运行时可观测性前置工作已经完成；文档记录的下一项转换行为工作是独立的 O1 优化切片，
  该切片尚未开始，也不代表完成 M3。在启动 O1 之前，必须保留
  `conversion-report.json` 中的可观测性契约，保留现有确定性产品门和 live 产品门，并为
  优化设定一个可测量目标。常规单元、契约、集成、doctor 和 live smoke 门不是 M3 Eval，
  但仍然是必需项。
- M3 Eval 扩展、经过授权并去标识化的真实样本资格验证、Gold 工作和外部人工评审，明确不在
  当前开发范围内。应将 M3 作为未来里程碑保留在 `docs/docfit-06-development-roadmap.md`
  中；不得声称 M3 已通过，也不得把它延后的开发门视为已完成当前计划的阻塞项。恢复这些
  工作之前，需要一份新的、经用户批准的计划。
- 可能使 00–06 中的声明失效的变更完成后，应使用 `$doc-keeper` 或等效的聚焦漂移检查。

## 环境设置与验证

```bash
uv sync --frozen
uv lock --check
uv build
uv run ruff check .
uv run mypy src
uv run pytest -q
uv run docfit doctor
```

当前累计 live Agent 证明还要求：

```bash
uv run docfit agent-smoke --case image
uv run docfit agent-smoke --case ask-user
uv run docfit agent-smoke --case denied-tools
uv run docfit agent-smoke --case path-tools
uv run docfit agent-smoke --case subagent
uv run docfit doctor --require agent-smoke
```

API 凭证只能保存在仓库外部的 `~/.config/docfit/agent.env` 中，文件权限必须为 `0600`。
绝不能在项目文档、测试、日志或示例中打印、提交或复制凭证值。

固定文档后端为：OfficeCLI 1.0.143，用于 inspect/edit/validate/edit feedback；Adobe PDF
Services（`pdfservices-sdk==4.2.0`），用于 baseline/candidate DOCX-to-PDF。交付转换不得
依赖本地 Microsoft Word、AppleScript、GUI 会话状态或本地字体。Adobe 缓存未命中会消耗
一次 Document Transaction；缓存命中不得重复调用 API。Adobe 字体环境应被视为由服务管理
且不透明。Adobe 转换会把完整的已授权 DOCX 上传到外部服务；绝不能发送不在当前任务授权
范围内的输入，也不能在日志中记录其文档正文。

## 工作规则

- 保持未匹配 Tool 的默认拒绝边界。只在明确且经用户批准的模块或架构契约替换现有公开
  Tool 名称之前，保留当前已批准的公开 Tool 名称；切换时必须原子替换调用方和测试，除非
  用户另行提出要求，否则不得增加旧别名。
- 主 Agent 在经过规范化路径检查后，可以使用受路径约束的 Read/Glob/Grep 访问项目 Skill
  参考、产品 Knowledge，以及当前任务的 input/work/output 根目录。主 Agent 还会获得受信任、
  自动批准、且不受 DocFit 路径门限制的 Bash 和 Write；这些 Tool 可以访问 Agent 进程可用的
  任何资源，包括直接 Read allowlist 之外的路径和环境值。这是一项明确的信任决策，不是
  sandbox 声明。绝不能在日志中打印凭证或文档正文。`docfit-unit-analyst` 不继承 Bash、
  Write 或主 Agent 文件 Tool。
- 直接、具体地沟通决策。先说明固定职责和可观察行为；不得用推测性实现细节、不必要的
  fallback 场景或杜撰的状态术语把已确定事实复杂化。优先使用“本次 Tool 调用失败且不发布
  任何输出”这样的表述，而不是“系统必须停止”这类抽象说法。
- 保持产品 Knowledge Package 的通用性，并随产品交付。学校要求、模板、格式参数和提取
  结论始终属于当前任务证据，绝不能自动提升为 Knowledge。
- 转换行为必须保持源文档只读，并使用当前任务授权的 work/output 目录；完成时重新检查
  源文件 hash。这是对受信任主 Agent 的产品规则，不是 Bash/Write 文件系统 sandbox。
- 不得增加第二个 Agent loop、工作流引擎、提问协议或推测性的 Provider 抽象。
- XML 风格的宿主控制 envelope 应视为编排器元数据；只有用户同时提供自然语言停止或
  改向意图时，才将其视为用户指令。
