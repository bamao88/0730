可以。这六类问题其实不是六个零散的 Word 技巧，而是六种经常被混淆的对象关系。它们分别回答：

| 问题 | 真正要回答的事情 |
|---|---|
| 内容所有权 | 这部分属于谁，最终应该保留、填写、生成、删除还是人工处理？ |
| 逻辑单元与物理分页 | 内容在语义上属于哪个单元，和它现在显示在哪一页，是不是一回事？ |
| 说明语义迁移 | 一段说明文字删除以后，它承载的规则有没有留下？ |
| 有效格式 | Word 最终实际采用了什么格式，而不是界面上挂了哪个样式名？ |
| 复合生成对象 | 看起来是一段文字的东西，实际上是不是由多个结构共同生成的？ |
| 分层验证 | 文件结构正确，是否真的意味着 Word 里结果正确？ |

## 1. 内容所有权

内容所有权不是版权意义上的“所有权”，而是：

> 这部分内容由谁提供、由谁控制，以及模板整理时应该怎样处置。

学校模板中的内容至少可能属于这些角色：

- 学校固定内容：校名、声明正文、表单标签、固定标题。
- 学生填写内容：姓名、题目、学号、摘要、正文等。
- 系统生成内容：目录、页码、自动编号、图表目录。
- 人工完成内容：签名、盖章、评语、审批意见。
- 模板说明内容：填写教程、格式说明、示例提示。
- 条件内容：只在某种论文类型或提交条件下出现。
- 来源不明的内容：目前无法确定应该保留还是删除。

例如声明页里同时可能有：

```text
学校固定声明正文
学生姓名
学生签名
填写说明
```

这四部分虽然在同一页，处置方式完全不同：

- 声明正文必须固定保留；
- 姓名应该成为自动填写槽位；
- 签名应该保留为人工区域；
- 填写说明可以从交付模板中清理，但其中的规则要先迁移。

最常见的错误是按表面特征处理：

- 红字全部删除；
- 方括号文字全部当占位符；
- 空白单元格全部当槽位；
- 整张声明页全部设为可编辑；
- 看见示例姓名就只删文字，不留下填写接口。

真正可泛化的原则是：

> 先识别内容角色和所有权，再决定处置方式；不能从颜色、字体或“是否为空”直接推出处理动作。

## 2. 逻辑单元与物理分页分离

逻辑单元回答的是：

> 这部分内容在论文结构中承担什么职责？

物理分页回答的是：

> Word 当前把它排到了哪一页？

二者不能等同。

例如：

- 封面是一个逻辑单元；
- 声明是另一个逻辑单元；
- 正文第一章和第二章通常仍共同属于正文逻辑单元；
- 一个表单可能跨两页，但仍然只是一个逻辑单元；
- 两个不同表单也可能共享同一物理页。

真实问题出现在自然分页上。假设源文件结构是：

```text
封面末尾
空段 A
空段 B
声明标题
```

在 Word 里可能实际呈现为：

```text
第 1 页：封面末尾 + 空段 A
第 2 页：空段 B + 声明标题
```

如果只看 XML，会以为声明标题前有两个空段。拆成独立模板后再增加一个显式分页，结果可能变成：

```text
第 1 页：封面
第 2 页：空段 A + 空段 B + 声明标题
```

于是声明页比原模板多一行。

这里真正的问题不是“该删几个回车”，而是：

- 空段 A 属于封面页末尾；
- 空段 B 属于声明页开头；
- 分页边界只能有一个所有者；
- 新文件边界已经承担分页职责时，不能再叠加原来的分页机制。

另一个常见误区是按章节拆逻辑单元。模板里有五章示例，不代表它有五种模板能力。五章可能只是同一种正文结构的五个重复实例。真正需要保留的可能只是：

- 一个能覆盖各级标题、正文、图表和公式的代表性章节；
- 一个页面方向或栏数确实不同的特殊正文变体。

所以抽象原则是：

> 先按内容职责确定逻辑单元，再分析分页、分节和空段怎样承载它；不能先按页切割，再反推内容结构。

## 3. 说明语义先迁移后删除

模板说明文字经常不应该出现在最终论文中，但这不代表它没有价值。

例如模板中写着：

```text
“目录标题前空三行，标题后空两行。”
“参考文献另页开始。”
“此页仅实名评审时填写。”
“附录为可选部分。”
```

如果只是删除这些说明文字，就会同时丢掉：

- 目录标题的前后间距；
- 参考文献的起页要求；
- 条件页面的适用条件；
- 附录的可选状态。

正确处理不是保留教程文字，而是把它承载的语义迁移到真正负责执行的地方：

| 说明中的语义 | 迁移目标 |
|---|---|
| 标题前后空行 | 段前、段后或版式约束 |
| 另页开始 | 分页或分节结构 |
| 必填、选填 | 槽位或区域的基数与缺失策略 |
| 实名评审时使用 | 条件区域 |
| 签字盖章 | manual 区域 |
| 目录包含三级标题 | 目录生成规则 |
| 装订顺序 | 模板逻辑单元顺序 |

北京大学案例更复杂：社区模板里的说明文字混合了五种东西：

- 学校要求声称；
- 标准或规范建议；
- 模板作者的实现方式；
- Word 操作教程；
- changelog、邮箱等维护信息。

它们不能整段照收，也不能整段删除。要先拆开性质：

- 真正规则迁移进模板结构或槽位索引；
- 实现方式只作为当前模板机制保留；
- 教程和维护信息可以删除；
- 证据不足的学校要求不能冒充已确认事实。

抽象原则是：

> “说明文字是否进入最终模板”和“说明文字是否携带有用语义”是两个不同问题。允许删除文字之前，必须先确认其规则已经有新的承载者。

## 4. 有效格式，而不是样式名

Word 中一个段落最终怎样显示，不只由它的样式名称决定。

简化以后，有效格式大致来自：

```text
文档默认值
→ 样式继承链
→ 当前命名样式
→ 段落直接格式
→ run 直接格式
→ 编号、内容控件等外层结构
```

越靠后的直接设置通常越可能覆盖前面的值。

例如一个段落挂着“正文”样式：

```text
正文样式：两端对齐
段落直接格式：左对齐
```

最终显示是左对齐，不是两端对齐。

另一个真实案例是“假居中”：

```text
段落对齐：居中
首行缩进：仍然存在
```

虽然 `jc=center` 是正确的，但缩进改变了可用版心，文字视觉中心仍然偏右。只检查“是否居中”会通过，检查最终几何才会发现问题。

目录的情况更典型：

```text
TOC 1 样式：加粗
旧目录缓存中的 run：显式取消加粗
```

旧目录看起来正常，是因为缓存结果抵消了错误样式。清除缓存、让 Word 重建目录以后，直接覆盖消失，目录就整体变粗。

因此不能简单得出：

```text
TOC 1 看起来正常
→ TOC 1 样式正确
```

正确结论应该是：

```text
当前缓存结果看起来正常
但重建后的有效格式取决于 TOC 样式
因此必须清除或重建缓存后再次验证
```

抽象原则是：

> 样式名只是格式来源之一。处理和验证都应面向最终生效属性，尤其要注意样式继承、直接覆盖、编号和生成结果缓存。

## 5. 复合生成对象原子处理

有些内容看起来像普通文字，实际上是由多个相互关联的结构共同生成的。

最典型的是目录。一个可用目录至少依赖：

```text
正文标题层级
+ 标题大纲级别
+ 自动编号
+ TOC 域指令
+ TOC 1/2/3 样式
+ 制表位与点引导符
+ 页码结果
+ 目录缓存
+ 更新策略
```

如果只保留目录文字，目录就不能更新。

如果只保留 TOC 域，却没有正确的标题大纲级别，目录内容会错。

如果域和标题都正确，但 TOC 样式有问题，Word 更新后版式仍会错。

所以目录不是“一组目录行”，而是一个复合生成对象。它应该整体理解、整体修改、整体验证。

同类对象还有：

- 自动编号：编号定义、编号实例和段落引用缺一不可。
- 参考文献引用：可见的 `[3]`、目标书签和内部链接是不同结构。
- 图表编号：题注文字、编号域、章号和交叉引用相互关联。
- 页码：页码域、分节、起始值和页眉页脚继承共同决定结果。
- 图片：绘图对象、媒体文件和 relationship 必须闭合。
- 内容控件：可见占位文字、唯一标签、范围和外层格式共同构成槽位。

真实案例中，参考文献编号 `[1]` 并不在正文字符里，而由 Word 编号系统生成。只比较文字，会认为内容完整；替换段落属性时删掉 `numPr`，所有编号却会静默消失。

所以“原子处理”不是说底层只能调用一次，而是：

> 在语义上把完整关系闭包当作一个对象；修改时不能只拿走其中可见的那一小块。

## 6. 结构完整性与目标渲染分层验证

验证 Word 文档至少有几个不同层次：

### 第一层：包和 XML 合法

检查：

- DOCX ZIP 能打开；
- XML 合法；
- relationship 目标存在；
- 图片、页眉页脚等部件没有丢失。

它只能证明文件没有明显损坏。

### 第二层：内容和结构完整

检查：

- 源内容块是否全部且只分配一次；
- 固定文字是否保留；
- 槽位是否唯一；
- 表格、字段、书签、编号、媒体关系是否完整；
- 是否出现遗漏、重复或未声明修改。

它可以发现“页面看起来正常，但丢了 37 个无文字结构块”这类问题。

### 第三层：语义行为正确

检查：

- 目录能否更新；
- 标题是否进入正确目录层级；
- 页码是否按分节连续；
- 参考文献链接能否跳到正确目标；
- 条件区域、必填和选填状态是否正确；
- manual 区域是否仍然只能人工处理。

这一层检查的是文档是否“会正确工作”。

### 第四层：目标应用中的可见结果正确

检查：

- 页数；
- 页首锚点位置；
- 空白页；
- 表格跨页；
- 字体和换行；
- 目录点引导线；
- 公式裁切；
- 页眉页脚和页码；
- 更新全部域之后的最终版式。

这是实际交付质量。

这些层次不能互相替代：

```text
XML 合法
≠ 内容完整
≠ 语义正确
≠ Word 中版式正确
```

真实案例中，同一份北京大学模板：

- LibreOffice 显示 15 页；
- Microsoft Word 显示 17 页。

LibreOffice 可以发现明显溢出和异常，但不能替代目标 Word 环境裁决分页、域和制表位。反过来，Word 里视觉正常也不能证明没有丢失关系、隐藏数据或源结构块。

因此抽象原则是：

> 程序验证负责确定性的结构不变量；目标渲染验证负责可见结果。两者都要通过，而且冲突时不能用其中一层掩盖另一层。

## 把六类问题合起来

它们可以压缩成一个统一思路：

```text
先确认这是什么、属于谁
→ 再确认它与相邻内容和页面的关系
→ 删除前迁移它承载的语义
→ 修改时保护完整结构关系
→ 以最终生效格式而非表面标签判断
→ 最后分别验证结构、行为和目标应用结果
```

因此写进 `docfit-school-extract` 的不应该是“遇到封面做什么、遇到声明做什么”的案例清单，而应该是这些跨对象、跨学校仍成立的处理原则。目录、页码、声明等具体案例，只用来解释这些抽象原则为什么存在。
