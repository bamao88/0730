# AI 协作中的完成层级与证据边界

本文应该回答：

- 为什么用户和 AI/研发经常对“完成、通过、闭环”产生不同理解；
- 如何从软件开发视角区分目标语言、证据语言和验收语言；
- 用户在提问、看汇报、判断进度时应该用什么视角；
- AI 在汇报时应该如何避免把局部完成包装成整体完成；
- 如何用“完成层级、验证证据、未完成、不能宣称”降低协作误解。

状态: human 协作方法记录
适用范围: 非研发用户与 AI/研发协作、软件开发进度判断、验收边界沟通

## 核心问题

这类误解不只是“AI 汇报不清楚”。它本质上是协作里的现实压缩问题。

用户作为需求方，关心的是：

```text
这件事是不是能用了？
风险是不是关掉了？
下一步是不是可以放心往后走？
```

研发或 AI 看到的是很多层：

```text
文档层
接口层
schema 层
runtime 层
测试层
数据层
质量层
发布层
```

当 AI 汇报时，它可能把某一层的进展压缩成一句话，例如“闭环了”“通过了”“修好了”。
问题是：这句话丢失了层级信息。用户听到的是产品承诺，AI 说的可能只是局部工程事实。

## 目标语言与证据语言

用户的语言通常是目标语言：

```text
我要能从单元阶段继续调试
我要最终模板可用
我要质量达标
```

AI 或研发的语言通常是证据语言：

```text
文档已写
测试已过
CLI 退出码 0
文件已生成
schema 校验通过
```

两种语言都对，但中间缺一个翻译层：

```text
这个证据是否足以证明那个目标？
```

以后遇到任何“完成了”“通过了”的说法，都可以追问：

```text
你现在给我的证据，证明的是哪个目标？
没有证明哪个目标？
```

## 完成是梯子，不是一个点

软件能力从想法到可交付，通常会经过多个梯级：

```text
1. 说清楚了：文档/方案层
2. 写出来了：代码/配置层
3. 跑起来了：执行层
4. 可复现了：测试/replay 层
5. 能恢复了：debug/runtime 层
6. 质量达标了：eval/human review 层
7. 可以交付了：产品验收层
```

AI 很容易站在第 1 或第 3 级说“完成了”。用户心里想的可能是第 6 或第 7 级。

所以看任何汇报时，不要先问：

```text
它是不是完成了？
```

而应该问：

```text
它现在站在第几级？
我要的是第几级？
中间缺哪几级？
```

## 局部真相与整体真相

研发默认的是局部真相，需求方默认的是整体真相。

例如 AI 说：

```text
文档闭环了
```

它可能真正想表达：

```text
关于这个设计的文档之间不矛盾了。
```

用户可能理解成：

```text
这个能力已经闭环了，可以用了。
```

解决办法不是让用户学会所有研发细节，而是建立一个固定规则：

```text
任何结论都要带范围。
```

## 用户看汇报的五个问题

用户看 AI 或研发汇报时，可以用这五个问题扫一遍：

```text
1. 它说完成的是哪一层？
2. 它拿什么证据证明？
3. 这个证据能不能证明我真正关心的目标？
4. 它有没有明确说哪些没做？
5. 下一步是不是依赖一个还没证明的前提？
```

如果汇报没有回答这些问题，说明汇报还不合格。

## 用户提问的推荐格式

用户不需要变成研发，但可以把目标翻译成验收边界。

不建议只说：

```text
解决这个问题。
```

更好的问法是：

```text
目标是：我需要后续调试能从已接受的单元 proof 后继续，不重新拆单元。
验收是：有命令能 --until unit-boundary 写 proof；有命令能 --from unit-boundary 继续；
hash 不匹配会失败；三校 replay 能证明。
这次只允许做到单元阶段，不要继续字段和最终模板。
完成后请分别说明：已完成、已验证、未完成、不能宣称。
```

这种问法不是要求用户懂所有技术细节，而是把业务目标变成可验收边界。

## 看结果时的判断方式

如果 AI 说文档完成，应该问：

```text
这是说明清楚了，还是能力实现了？
```

如果 AI 说测试通过，应该问：

```text
测的是小单元、集成流程，还是真实输入？
```

如果 AI 说文件生成，应该问：

```text
只是存在，还是能打开、schema 通过、质量评分通过？
```

如果 AI 说修复了，应该问：

```text
修的是 Agent、Tool、Harness、Runtime、Eval 哪一层？
```

如果 AI 说跑通了，应该问：

```text
跑到哪个 checkpoint？
有没有继续到最终产物？
有没有质量验收？
```

## AI 汇报格式

为了避免把局部状态包装成整体完成，AI 应该尽量使用这种汇报格式：

```text
完成层级：
- 文档层 / 代码层 / 测试层 / runtime 层 / 产品验收层

本次实际完成：
- ...

验证证据：
- 命令 / 文件 / proof / report

还没完成：
- ...

不能宣称：
- ...
```

其中“不能宣称”很重要。它可以防止“局部进展”被误解成“整体目标已完成”。

## 用户的有效角色

用户的角色不是技术细节审查者，而是验收定义者。

用户不需要知道每个 locator、schema、pytest 的细节，但需要不断把问题拉回：

```text
这个证据证明了哪个业务目标？
还有哪个目标没有被证明？
```

这就是非研发视角最有力量的地方。研发或 AI 容易沉在细节里，用户要负责防止“细节完成”
被误当成“目标完成”。

## 一句话总结

用户不需要追上 AI 的全部技术细节。用户需要要求 AI 把每个技术结论绑定到：

```text
完成层级
验证证据
未覆盖范围
不能宣称的内容
```

这样才能看懂进度，也能避免被“通过了”“完成了”“闭环了”这些压缩词误导。
