# AI 协作中的复杂度判断

状态: human-facing 讨论笔记
更新日期: 2026-08-20

本文记录一个协作判断框架：当一个任务看起来很简单，但 AI 提出 `index`、`schema`、`validator`
或 `wrapper` 等工程词时，如何判断这是必要的复杂度，还是过早复杂化。

这些词听起来都像“工程上更严谨”，但它们实际代表不同成本级别。

## 成本层级

### 当前目录约定

含义：大家约定文件就放在固定路径，例如：

```text
<unit>/run/input/...
```

适合：只有当前人手工调试、输入数量少、失败后人工能立刻看懂。

成本最低。

### index 里声明 path/hash/proof

含义：把“这个单元用哪个输入、哪个 checkpoint、hash 是什么”写成一张清单，减少口头解释。

适合：有多个单元、会反复跑、AI 或人容易拿错文件。

成本很低，但比纯目录约定多一份清单。

### schema

含义：规定这张清单必须长什么样，字段名不能随便变。

适合：多个人或多段代码都会消费这个文件。

成本中等。

### validator

含义：写一个检查器，自动证明“清单里的路径都存在、hash 都匹配、checkpoint 能恢复”。

适合：一旦拿错输入会浪费很多调试时间，或者要放进 CI。

成本中等偏低，价值通常很实在。

### wrapper

含义：用户不再拼命令，只执行一个脚本，例如：

```text
run-post-unit 04-paper-body
```

适合：命令很长、参数容易错、会重复跑很多次。

成本中等，但能明显减少操作错误。

## 判断问题

判断是“用户把事情想简单了”，还是“AI 把事情想复杂了”，可以先看三个问题。

1. 错一次的代价高不高？

   如果错一次只是 1 分钟，目录约定够了。  
   如果错一次会让 Agent 跑半小时然后污染结论，至少要 index 或 validator。

2. 谁在消费这个东西？

   只有当前人手工跑：简单约定。  
   AI、脚本、CI、多线程任务都要跑：需要机器可读契约。

3. 这个动作会重复多少次？

   跑 1-3 次：别复杂化。  
   跑 10 次以上：wrapper 或 validator 往往划算。

## 当前模板提取最小单元调试的定级

对于 0820 的 6 个最小单元 checkpoint 调试，可以这样定级：

```text
目录约定：必须有，已经够后续人工/AI按固定路径跑。
index：可以保留，因为它成本低，方便总览。
schema：现在不必做。
validator：如果后续真要调 100 次，值得做一个很薄的。
wrapper：如果发现 AI/人还会拼错命令，就做；否则先不做。
```

因此，这类场景的默认策略不是立即上长期机制，而是先用固定目录结构；如果再次发生拿错输入或拼错命令，
再补一个很薄的 validator 或 wrapper。
