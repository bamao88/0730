# DocFit Skill 设计（04）v1.0

> 状态：现在实施
> 日期：2026-07-30
> 原则：Skill 是 Agent 的领域操作手册，不是工作流定义。

## 1. Skill 在架构中的位置

Skill 是 DocFit 最重要、迭代最频繁的产品资产。它把论文处理经验交给 Claude Agent，但把执行权留给 Agent SDK 与 Agent。

一个好的 Skill 回答：

- 用户想完成什么；
- 开始前要确认什么；
- 应读取哪些 Knowledge；
- 可使用哪些 Tools；
- 哪些判断可以自主完成；
- 哪些情况应回看、重试或询问用户；
- 什么结果可以称为完成；
- 哪些行为绝对禁止。

Skill 不定义：

- 固定阶段 ID；
- 阶段输入输出协议；
- 状态转换；
- checkpoint；
- 任务队列；
- 学校具体字号、页边距和固定文案；
- OOXML 实现细节。

## 2. `convert-thesis`

### 2.1 触发

当用户要求论文排版、套用学校模板、按学校要求修改格式或检查转换结果时触发。

输入通常包括：

- 学生论文 DOCX；
- 目标学校；
- 可选的学校版本；
- 可选的学生信息或用户补充说明。

### 2.2 目标

在不覆盖源文件、不静默丢失学生内容的前提下，生成：

- 最终 DOCX；
- 可用时的 PDF 和页面预览；
- 简短 validation 摘要；
- 仍需用户确认或人工查看的问题。

### 2.3 建议处理思路

Skill 应把下面内容写成可调整的建议，而不是必须逐步提交的流程：

1. 确认输入文件可读，并找到目标学校 Knowledge。
2. 使用分析工具理解论文结构、可见对象和现有样式。
3. 读取学校要求，识别学生内容与目标模板之间的差异。
4. 优先在学生正文原位置调整样式，避免不必要的复制和重建。
5. 需要前置模板时，使用工具填充明确槽位并保留学校固定结构。
6. 渲染并检查高风险页面，如封面、目录、跨页表格和参考文献。
7. 使用验证工具检查源文件未变、最终文件可打开、关键内容仍在、占位符已处理。
8. 如果证据不足，向用户提出最小问题；如果仍有风险，在最终回复中清楚说明。

Agent 可以根据文档实际情况跳过、重复或调整这些动作。

### 2.4 关键判断原则

- 学校具体格式只从目标学校 Knowledge 读取；
- 先观察再修改，不凭文件名或段落序号猜测；
- 语义判断由上下文、页面、样式和相邻内容共同支持；
- 能局部修改时不整体重建；
- 无法可靠定位时重新 inspect，不扩大修改范围；
- 学生文字与学校固定文字冲突时，优先保护学生内容并询问；
- 渲染结果与结构检查冲突时，两者都要呈现，不静默选择；
- 目录和页码依赖具体 Word 渲染时，明确人工复核要求。

### 2.5 必须询问或停止

以下情况不应靠 Agent 猜测：

- 找不到目标学校 Knowledge；
- 学校来源材料互相冲突且 Knowledge 未给出结论；
- 无法确认正文边界并可能导致内容删除；
- 出现 Tool 未支持的可见对象；
- 必填学生信息缺失；
- 字体或渲染环境使分页证据不可信；
- 修改工具报告定位歧义或结构损坏；
- 用户要求覆盖原文件。

能通过最小澄清继续时提问；存在内容损坏风险时停止修改并说明。

### 2.6 完成条件

Skill 可以在以下条件满足时向用户报告任务完成：

- 源文件未被覆盖；
- 最终 DOCX 存在且能重新打开；
- 关键学生内容检查未发现丢失；
- 已应用目标学校的关键格式和模板要求；
- 必填占位符和模板说明文字已处理；
- 能生成时，预览文件已生成；
- 严重 Tool 错误已解决；
- 未解决的不确定项已明确告诉用户。

“完成”不要求一套自定义 delivery state。Agent 的最终回复应直接引用实际产物和 validation 结果。

## 3. `prepare-school-template`

### 3.1 触发

当用户要求导入新学校、整理官方模板、提取学校格式要求或更新学校资料时触发。

### 3.2 目标

产出一个可供 `convert-thesis` 读取的学校 Knowledge 包，包括：

- 来源文件；
- 面向 Agent 的学校说明；
- 工具需要的结构化格式配置；
- 可复用模板；
- 少量已确认示例；
- 版本与适用范围。

### 3.3 建议处理思路

1. 保存官方模板和文字/PDF 要求的来源信息。
2. 使用 Tool 分析模板结构和实际格式。
3. 对照多个来源，提取确定要求并列出冲突。
4. 需要时向学校资料审核者确认冲突。
5. 生成最小 Knowledge 包。
6. 用一份合成论文验证它能被 `convert-thesis` 使用。
7. 人工打开模板和示例结果确认后提交版本控制。

这同样是 Agent 的操作建议，不是学校发布工作流。

### 3.4 模板文字分类

处理学校模板时通常区分：

```text
fixed_content       最终必须保留的学校固定文字
conditional_content 根据学生类型决定是否出现
slot_placeholder    等待学生内容填入的位置
format_instruction  只用于说明格式、最终应清理的文字
```

无法可靠分类时保留原文并询问，不猜测性删除。

## 4. Skill 目录

```text
skills/
├── convert-thesis/
│   ├── SKILL.md
│   ├── references/
│   │   ├── conversion-guide.md
│   │   └── pitfalls.md
│   └── scripts/              # 仅在确有轻量辅助脚本时存在
└── prepare-school-template/
    ├── SKILL.md
    ├── references/
    │   ├── extraction-guide.md
    │   └── pitfalls.md
    └── scripts/
```

Tool 实现不复制到 Skill。Skill 中的脚本只做本 Skill 特有的轻量准备；通用 DOCX 能力进入 `tools/`。

Knowledge 不放在 references 中。references 是通用方法，`knowledge/schools/` 才存学校事实。

## 5. 写作规范

1. `description` 写清触发条件，让 Agent 能正确发现 Skill。
2. 正文保持短小，只保留高频且重要的指引。
3. 复杂背景、示例和陷阱按需放入 references。
4. 使用目标、原则和检查清单，不使用固定状态图。
5. 每条规则尽量能追溯到真实样本或学校来源。
6. 明确允许 Agent 适应的范围和不可突破的底线。
7. Tool 名称和用途写清楚，参数细节留在 Tool schema。
8. 学校具体要求只通过 Knowledge 获取。
9. 发现重复失败时先补 Eval，再修改 Skill。
10. 删除已经由 Tool 前置条件或 SDK 能力保证的重复说明。

## 6. Skill 评审问题

- Agent 是否知道目标，而不只是知道步骤？
- 指引是否给 Agent 留出适应文档差异的空间？
- 学校事实是否被误写进通用 Skill？
- OOXML 细节是否泄漏到 Skill？
- 是否出现固定阶段、状态或 checkpoint 设计？
- 失败后应该改 Skill、Knowledge 还是 Tool，边界是否清楚？
- 这条新增规则是否有真实样本或 Eval 支持？

如果 Skill 需要一张复杂状态图才能解释，应先检查是否已经把 Agent 任务重新设计成工作流。
